# 棋譜インデクスと前例検索

## 概要

ユーザーが登録したディレクトリ以下の棋譜ファイルから局面のインデクスを作り、
現在の局面と一致する局面が出現する棋譜 (前例) を検索する機能。
デスクトップアプリ (Electron 版) 専用の機能であり、Web アプリでは利用できない。

この文書は設計段階のものであり、まだ実装されていない。
実装の際にベンチマークの計測結果などを踏まえて更新する。

## 方針

- インデクスの作成 (棋譜のパースと局面ハッシュの計算) は Rust で実装した WebAssembly で行う。
  既存の定跡の WebAssembly 版 (`specs/book-wasm.md`) の基盤を流用する。
- 実装は WebAssembly 版だけとし、JavaScript (tsshogi) 版は作らない。
  WebAssembly 版で読めない棋譜は tsshogi にフォールバックせず、エラーとして記録する。
- 対応する形式は KIF・KI2・CSA・JKF の優先順位で増やす。アルファ版では KIF・KI2・CSA に対応する。
- 作成と検索は utilityProcess で動かし、メインプロセスを止めない。
- 対象ディレクトリ (ルート) ごとに独立したインデクスを持つ。
- ファイルの増減は、実ファイルとマニフェストの突き合わせ (再スキャン) で反映する。
  ファイル監視は再スキャンを早めるきっかけとしてのみ使う。
- ShogiHome 自身が書き込んだ棋譜ファイルは、書き込みの直後にインデクスホストへ通知して反映する。
  保存処理そのものは変更しない。
- インデクスは古い可能性があることを前提とし、棋譜を開く時点で tsshogi で読み直して確かめる。
- UI の主な導線は、現在の局面に追従する「前例」タブとする。
- 前例の棋譜はメインウィンドウの棋譜を置き換えず、別ウィンドウ (前例ビューア) で開く。

## 技術方式

### JavaScript (tsshogi) での実測

tsshogi 2.x で 120 手の棋譜をパースし、全局面の SFEN を作る時間 (1 スレッド)。

| 形式 | パースのみ | パース + 全局面の SFEN |
| ---- | ---------- | ---------------------- |
| KIF  | 1.10 ms/局 | 1.41 ms/局             |
| CSA  | 0.97 ms/局 | 1.31 ms/局             |

1 コアで毎秒約 700 局であり、10 万局で約 2.5 分、100 万局で約 25 分かかる
(読み込み・文字コード判定・ソート・書き出しは含まない)。
主なコストは、tsshogi が指し手ごとにオブジェクトを生成することにある。
Rust で、メモリを確保せずに差分でハッシュを更新すれば、1 局あたり数十 µs に収まる見込みである
(未計測。ベンチマークで確かめる)。その場合、ボトルネックはファイル I/O に移る。

### 方式の比較

| 方式                                  | 速度                           | 配布・保守                                                 | Web 版 | 評価                      |
| ------------------------------------- | ------------------------------ | ---------------------------------------------------------- | ------ | ------------------------- |
| JavaScript (tsshogi) + worker_threads | 約 700 局/秒/コア              | 容易                                                       | 可     | 不採用 (性能が不足する)   |
| Rust → WebAssembly + 複数ワーカー     | ネイティブの 1.5〜2 倍程度遅い | wasm 1 つで全 OS に対応。基盤は既存                        | 可     | **採用**                  |
| ネイティブアドオン (napi-rs など)     | 最速                           | OS・CPU ごとのビルドと署名、Electron の ABI への追従が必要 | 不可   | wasm で不足する場合に検討 |
| 別プロセスの実行ファイル              | 最速                           | ネイティブアドオンと同じ配布の負担                         | 不可   | 不採用                    |

WebAssembly を採用する理由:

- `wasm/book` に局面 (`board.rs`)・指し手 (`moves.rs`)・Packed SFEN (`packed.rs`) の実装があり、
  ツールチェーンの固定・CI でのバイト一致検証・ライセンス表示の仕組みもそのまま使える。
- 処理はファイル単位で独立しているため、wasm のスレッド (SharedArrayBuffer) は使わず、
  独立したインスタンスを複数のワーカーで並列に動かせば足りる。

### プロセス構成

```
renderer ──IPC──▶ background (main)
                    │ 起動・中断・進捗の中継
                    ▼
            utilityProcess (棋譜インデクスホスト)
              ├─ ディレクトリの走査、マニフェストとの差分の計算 (JavaScript)
              ├─ worker_threads × min(コア数 - 1, 4)
              │    読み込み → 文字コード変換 (JavaScript) → パースとハッシュ列の生成 (wasm)
              │    → ソート済みのランを出力
              ├─ ランの k-way マージ → セグメントファイルの書き出し
              └─ 検索ワーカー (worker_threads)
                   走査 → 集計 → 並べ替え → 検索結果の保持 (「検索」を参照)
```

utilityProcess にする理由は、メインプロセスを止めないこと、異常終了してもアプリ全体を巻き込まないこと、
kill で確実に中断できることである。

### 役割分担

- JavaScript: ファイルの列挙と読み込み、文字コード変換。
  文字コード変換にはアプリと同じ `decodeRecordFileContent` (`src/common/file/record.ts`) を使い、
  拡張子ごとの既定の文字コードとアプリ設定 `textDecodingRule` に従う (前例ビューアやメインウィンドウと同じ規則で読むため)。
  文字コード変換を Rust に持たせると、変換テーブルの分だけ wasm が大きくなり、依存クレート無しの方針にも反する。
- WebAssembly: 棋譜のパース、局面の更新、局面ハッシュの差分計算、エントリー列の生成とソート。

### 対応形式

| 優先順位 | 形式                 | 対応する版     | Rust での実装の要点                                                          |
| -------- | -------------------- | -------------- | ---------------------------------------------------------------------------- |
| 1        | KIF (`.kif` `.kifu`) | アルファ版     | ソフトごとの書き方の違い、盤面図 (BOD) からの開始、手合割、変化の節          |
| 2        | KI2 (`.ki2` `.ki2u`) | アルファ版     | 「右」「左」「直」「上」「引」「寄」などの相対表記の解決に指し手の生成が必要 |
| 3        | CSA (`.csa`)         | アルファ版     | V2・V3                                                                       |
| 4        | JKF (`.jkf`)         | アルファ版の後 | 依存クレートを使わないため、最小限の JSON パーサーが必要                     |

- 対応していない形式は、ルートのオプションの対象形式に表示しない。
- `.sfen` はアプリが読み込みに対応していないため対象にしない。
- WebAssembly 版で読めないファイル (未知の書き方・壊れたファイルなど) は、マニフェストにエラーとして記録し、
  インデクスには入れない。tsshogi にはフォールバックしない。
  エラーになったファイルは管理ダイアログで確認できるようにし、Rust のパーサーの改善で対応する。

### 正しさの担保

- 単体テストで、同じ棋譜から tsshogi と WebAssembly 版で同じハッシュ列が出ることを golden 比較で確かめる。
  tsshogi はテストでのみ使い、インデクスの作成には使わない。
- 前例ビューアは tsshogi で棋譜を読むため、開く時点で局面を比べて確かめる (「検索結果が古い場合の扱い」)。
  ハッシュの衝突はここで検出できるため、局面キーは 64 bit で足りる。
  Rust のパーサーと tsshogi の解釈が違う場合もここで一致しなくなる。これは Rust のパーサーの不具合として修正する。

### Rust クレートの構成

`wasm/` を Cargo ワークスペースにし、局面・指し手・Zobrist ハッシュを共有クレートに切り出す。
KI2 の相対表記の解決に必要な指し手の生成も共有クレートに置く。
`book.wasm` と `record-index.wasm` は別のモジュールとしてビルドし、定跡モジュールのサイズと検証に影響させない。

## インデクス

### 局面キー

- 盤面・持ち駒・手番から計算する 64 bit の Zobrist ハッシュ。手数は含めない
  (手順前後で同じ局面になった棋譜もヒットさせるため)。
- 1 局の中で同じ局面が複数回出現する場合 (千日手など) は、最初の手数だけを記録する。
- 分岐 (変化) を含めるかは作成時のオプションとする (既定は本譜のみ)。
- 左右反転などの関連局面は、インデクスを変えずに検索時のキーを増やして扱える。

### ファイル配置

```
userData/record-index/
  roots.json          登録済みルートの一覧 (atomic.ts の方法で更新する)
  <rootId>/
    manifest.<gen>    ファイル一覧と、有効なセグメントの一覧
    seg-<n>.idx       エントリー (一度書いたら変更しない)
```

`roots.json` の各エントリー:

| フィールド | 内容                                             |
| ---------- | ------------------------------------------------ |
| `id`       | ルートの ID                                      |
| `path`     | 登録されたパス                                   |
| `realPath` | 正規化したパス (重複判定に使う)                  |
| `options`  | サブディレクトリを含むか、対象形式、分岐を含むか |
| `lastScan` | 最後にスキャンした日時                           |
| `status`   | 状態 (最新 / 更新中 / 利用不可)                  |

### マニフェスト

ファイルごとに次の情報を持つ。

| フィールド | 内容                                                             |
| ---------- | ---------------------------------------------------------------- |
| `relPath`  | ルートからの相対パス                                             |
| `size`     | ファイルサイズ                                                   |
| `mtimeNs`  | 更新日時                                                         |
| `fileKey`  | ファイルの識別子 (dev + ino、Windows ではファイル ID)            |
| `gameIds`  | ファイルに含まれる棋譜の ID (1 ファイルに複数局を含む場合がある) |
| `error`    | 読み込みに失敗した場合のエラー                                   |

棋譜ごとに、前例タブの一覧表示に使うメタ情報 (対局者・日付・結果・棋戦など) を持つ。
ディレクトリごとに、簡易スキャンで使う mtime を持つ。
ファイルの一覧はディレクトリ単位でまとめ、パスの順に並べて持つ (完全スキャンでマニフェスト全体を
メモリに読み込まないため。「メモリ」を参照)。
メタ情報のうち、集計と並べ替えに使う結果と日付は列ごとの型付き配列として持つ。
対局者やパスなどの文字列は位置表を介して参照し、一覧のページを返すときに必要な分だけディスクから読む。
無効になった gameId はビットマップで持つ。gameId は再利用しない。

### セグメント

- 局面ハッシュでソートした (hash, gameId, ply, nextMove) の列。
  `nextMove` は前例タブで次の手ごとの集計を表示するために持つ。
- ハッシュの上位ビットによるバケット表と、差分符号化で圧縮する。
  未圧縮で 1 エントリー約 16 byte、10 万局 × 120 手で約 190 MB。圧縮すれば半分程度になる見込みである。
- 検索はバケット表で範囲を決め、その範囲だけをファイルから読む (メモリに全体を読み込まない)。
- 件数と集計を先に返し、一覧はページ単位で返す (「検索」を参照)。
- SQLite (`node:sqlite`) は、1 億行規模で容量と挿入速度が見合わないため使わない。

## ルートの管理

### 追加

- 新しい `rootId` を発行し、空のマニフェストを作ってから初回の作成を始める。
  作成の途中でも、完成したセグメントの分は検索できる。
- 登録時に `realpath` で正規化して既存のルートと比べる (Windows と macOS では大文字小文字を区別しない)。
  - 既存ルートの内側にあるディレクトリは、重複になるため登録を拒否する。
  - 既存ルートの外側にあるディレクトリは、内側のルートを置き換えるか確認する。
    置き換える場合は、内側のマニフェストとセグメントのパスに接頭辞を付けて引き継ぐ (作り直さない)。
- シンボリックリンクとジャンクションは、既定では辿らない (循環と二重登録を防ぐため)。

### 削除

`roots.json` から外し、`<rootId>/` を丸ごと削除する。他のルートには影響しない。

### ルートが見つからない場合

外付けドライブやネットワークドライブが外れている場合など。

- インデクスは削除せず、状態を「利用不可」にする。
- 検索結果ではグレー表示にし、棋譜は開けないようにする。
- ルートの場所を変更する操作を用意する。マニフェストは相対パスで持つため、ルートのパスを書き換えるだけで済む。

### 検索

全ルートのセグメントを検索して結果を結合する。

#### 流れ

```
renderer (前例タブ)             main            インデクスホスト (utilityProcess)
                                                  ├─ メインスレッド: 振り分け・検索セッションの表
 search(sfen) ──invoke──▶ 中継 ──postMessage──▶  └─ 検索ワーカー (worker_threads)
   ◀── {searchId, total, 集計} ───────────────────     走査 → 集計 → 並べ替え → 結果を保持
 getPage(searchId, offset, limit) ──▶ … ──▶ 保持している結果から切り出して返す
 cancel(searchId) / 新しい検索 ──▶ … ──▶ 中断フラグを立てて結果を破棄する
```

ヒット数の多い局面 (初期局面など) では、走査・集計・並べ替えに数十〜数百 ms かかる見込みである。
これをホストのメインスレッドで行うと、その間は保存時の通知・作成の進捗・新しい検索要求を処理できないため、
検索は専用のワーカースレッド (検索ワーカー) で行う。

#### WebAssembly の検索 API

定跡の保存 (`sbk_save_begin` / `sbk_save_next`) と同じく、少しずつ進める形にする。

```
search_begin(hash_lo, hash_hi) -> handle   バケット表で読む範囲を決める
search_next(handle, max_entries) -> n      最大 max_entries 件の (gameId, ply, nextMove) を結果領域に書く。0 なら終わり
search_end(handle)                         状態を解放する
```

検索ワーカーは、これをジェネレーターで包んで使う。

```ts
function* scan(hash: bigint, cancel: Int32Array): Generator<Uint32Array> {
  const h = wasm.search_begin(lo(hash), hi(hash));
  try {
    while (Atomics.load(cancel, 0) === 0) {
      const n = wasm.search_next(h, 4096);
      if (n === 0) return;
      yield readResult(n); // wasm のメモリからコピーして返す
    }
  } finally {
    wasm.search_end(h); // 中断・例外・正常終了のいずれでも解放する
  }
}
```

- 中断は、ホストのメインスレッドと共有する `SharedArrayBuffer` のフラグで伝える。
  検索ワーカーはメッセージの受信に頼らず、一定件数ごとにフラグを確かめて止まる。
- 検索ワーカーは走査しながら、無効な gameId の除外、次の手ごとの局数と勝敗の集計、結果の一覧
  (gameId と手数の `Uint32Array`) の蓄積を行う。勝敗はマニフェストの結果を型付き配列で持って参照する。
- 最後に結果の一覧を並べ替える (既定は日付の新しい順)。

#### 検索セッション

ページを要求するたびに検索し直す方式 (ステートレスなカーソル) は、ヒット数の多い局面でページごとに
走査と並べ替えをやり直すことになるため採らない。検索結果は検索ワーカーが `searchId` ごとに保持する
(100 万件で 8 MB 程度)。

| API                                | 内容                                                                                  |
| ---------------------------------- | ------------------------------------------------------------------------------------- |
| `search(sfen)`                     | 走査・集計・並べ替えが終わったら `{ searchId, total, 次の手ごとの集計, 勝敗 }` を返す |
| `getPage(searchId, offset, limit)` | 保持している結果から切り出し、メタ情報 (対局者・日付・パスなど) を付けて返す          |
| `cancel(searchId)`                 | 中断フラグを立て、保持している結果を破棄する                                          |

- 前例タブ 1 つにつき保持する検索セッションは 1 つとする。新しい検索が来たら前の検索を中断して破棄する。
- 前例タブを持つ renderer (webContents) が破棄されたときにも破棄する。
- 一定時間使われなかった検索セッションも破棄する。

#### 検索中のインデクスの更新

- 検索セッションは、開始した時点のマニフェストの世代を固定して読む。ページの取得でも同じ世代を使う。
- 検索セッションが参照している世代のセグメントは削除しない (参照カウントで管理する)。
  Windows では開いているファイルを削除できないため、この管理が必要である。
- 保持している結果が少し古くなることはあるが、前例ビューアで開く時点で確かめるため問題にならない。

## ファイルの増減の扱い

### 突き合わせ

スキャンした実ファイルとマニフェストを比べ、次のように処理する。
比較はディレクトリ単位で、実際の列挙結果とマニフェストをパスの順に突き合わせて行う。

| 判定           | 条件                                             | 処理                                             |
| -------------- | ------------------------------------------------ | ------------------------------------------------ |
| 追加           | マニフェストに無い                               | 新しい gameId を振り、新しいセグメントに入れる   |
| 削除           | 実ファイルが無い                                 | gameId を無効にする (セグメントは変更しない)     |
| 変更           | `size` または `mtimeNs` が違う                   | 古い gameId を無効にし、新しい gameId で作り直す |
| 移動・名前変更 | パスは違うが `fileKey`・`size`・`mtimeNs` が一致 | マニフェストのパスだけを書き換える               |

1 ファイルに複数局を含む場合 (CSA の `/` 区切りなど) は、ファイル単位でまとめて作り直す。

### スキャンの種類

- 簡易スキャン: マニフェストに記録したディレクトリをすべて stat し、mtime が記録と違うディレクトリだけを列挙する。
  ディレクトリの mtime は直下での追加・削除・名前変更で更新される (NTFS・APFS・ext4) が、
  孫ディレクトリでの変更では更新されないため、記録したディレクトリは階層によらずすべて stat する。
  既存ファイルの内容の書き換えは検出できない。
- 完全スキャン: 全ファイルを stat する。

### ShogiHome 自身による書き込みの通知

ShogiHome の保存処理 (`src/background/window/ipc.ts` の `SAVE_RECORD`) は `fs.writeFile` で直接上書きするため、
上書き保存ではディレクトリの mtime が変わらず、簡易スキャンでは検出できない。
ファイル監視が効かない環境では完全スキャンまで反映されないことになるため、
background で棋譜ファイルを書き込む箇所から、書き込みの完了後にインデクスホストへパスを通知する。

- 通知する箇所:
  - `SAVE_RECORD` (上書き保存・名前を付けて保存・対局棋譜の自動保存)
  - 一括変換の出力 (`src/background/file/conversion.ts`)
- インデクスホストは、パスが登録済みのルートの内側にあれば、そのファイルだけを突き合わせの「追加」または
  「変更」として扱い、すぐに作り直す。ルートの外側であれば何もしない。
- 一括変換のように大量に書き込む場合は、通知をまとめて処理する。
- 同じファイルについて通知とファイル監視の両方が届いても、`size` と `mtimeNs` がマニフェストと一致すれば
  処理を省くため、二重に作り直すことはない。
- 通知は書き込みの成否に影響させない。インデクスホストが動いていない場合や通知に失敗した場合は無視し、
  スキャンで反映する。
- 保存処理そのもの (書き込み方法) は変更しない。

| ------------------------------------------- | ---------------------------------------------------- |
| ルートの追加                                | 初回の作成                                           |
| ShogiHome 自身による書き込み                | 該当ファイルだけを直ちに作り直す                     |
| アプリの起動後 (少し遅らせて、低い優先度で) | 全ルートの簡易スキャンと差分更新                     |
| 前例タブの表示                              | 前回のスキャンから一定時間が経っていれば簡易スキャン |
| 起動中のファイル監視                        | 通知を数秒まとめ、該当ディレクトリだけ再スキャン     |
| 手動の再スキャン                            | 完全スキャン                                         |

アプリの起動中でなければファイル監視は変更を捕捉できず、ネットワークドライブや Linux の inotify の上限で
取りこぼしも起きるため、監視だけには頼らない。
自動更新は設定で無効にできるようにする。

## 一貫性と同時実行

- 書き込みは棋譜インデクスホストだけが行い、ルート単位で直列化する。
  複数のアプリを起動した場合に備え、ルートごとに `proper-lockfile` で排他する。
- 世代管理: 更新は「セグメントを書く → `manifest.<gen+1>` を atomic に書く → 古い世代を削除する」の順で行う。
  途中で異常終了した場合は、次回の起動時に、どの世代からも参照されていないセグメントを削除する。
- 検索は開始時点の世代を読む。更新中でも検索できる。古い世代の削除は、その世代を参照する検索セッションが
  無くなるまで待つ。
- 無効な gameId の割合やセグメントの数がしきい値を超えたら、バックグラウンドでセグメントを統合する。

## メモリ

インデクス本体 (100 万局でディスク上 1〜2 GB) はメモリに読み込まない。
以下は 100 万局・1 局平均 120 手・1 エントリー 16 byte を前提とした見積もりであり、ベンチマークで計測して置き換える。
10 万局ではおおむね 1/10 になる (プロセス自体の分を除く)。

### 状態ごとの使用量

| 状態                          | 増える分                                  | 内訳                                                          |
| ----------------------------- | ----------------------------------------- | ------------------------------------------------------------- |
| 何もしていない (ホストが常駐) | 約 50〜70 MB                              | utilityProcess 自体 30〜50 MB、インデクスの常駐データ約 20 MB |
| 検索中・検索結果を保持中      | + 約 30〜50 MB                            | 検索ワーカー 20〜30 MB、検索セッション 1 件あたり最大約 16 MB |
| インデクスの作成中            | + 約 40 MB × ワーカー数 (4 本で約 160 MB) | ワーカー 1 本あたりの内訳は下記                               |
| 前例ビューアを開いている      | + 約 100 MB                               | Chromium の renderer プロセス 1 つ分                          |

### インデクスの常駐データ

| 項目                                                      | 100 万局でのサイズ |
| --------------------------------------------------------- | ------------------ |
| 集計と並べ替えに使う列 (結果 1 byte、日付 4 byte)         | 5 MB               |
| 無効な gameId のビットマップ                              | 0.1 MB             |
| 対局者・パスなどの文字列の位置表 (本体はディスクから読む) | 8 MB               |
| バケット表 (約 256 エントリーにつき 1 つ)                 | 2〜5 MB            |

### 検索セッション

- 結果 1 件につき gameId と手数で 8 byte。全局がヒットする局面 (初期局面など) では 100 万件で 8 MB になる。
- 並べ替えの間だけ、並べ替えのキーとして同程度が一時的に増える。

### インデクスの作成中

ワーカー 1 本あたり:

| 項目                                            | サイズ   |
| ----------------------------------------------- | -------- |
| V8 の isolate と WebAssembly のインスタンス     | 約 20 MB |
| ソート前に溜めるラン (100 万エントリーで区切る) | 16 MB    |
| 読み込んだファイル                              | 数十 KB  |

- ワーカーの数は `min(コア数 - 1, 4)` を上限とする。
- ランのマージでは、読み込みバッファをラン 1 つにつき 256 KB 程度とし、ランが多い場合は複数段に分けて
  マージして数十 MB に抑える。

### 対策

- 完全スキャンでマニフェスト全体をメモリに読み込まない。100 万ファイル分のパスを `Map` で持つと約 200 MB になる。
  マニフェストをディレクトリ単位でパスの順に持ち、実際の列挙結果と順に突き合わせることで、
  メモリに載るのを一度に 1 ディレクトリ分にする。
- WebAssembly のメモリは一度増えると縮まないため、作成が終わったら作成用のワーカーを終了する。
  検索ワーカーでも WebAssembly 側のバッファは固定サイズとし、結果の一覧は JavaScript の型付き配列で持つ。
- ホストは必要になってから起動する。前例タブが表示されておらず、作成も監視もしていない状態が一定時間続いたら
  終了してよい。再起動時はバケット表と列を読み込むだけで済む (1 秒未満の見込み)。
- 検索ではセグメントファイルを部分的に読むため OS のページキャッシュが空きメモリを使うが、
  OS が必要に応じて解放するため、アプリのメモリ使用量には数えない。

## 検索結果が古い場合の扱い

前例ビューアで棋譜を開く時点で tsshogi で読み直して確かめる。

- ファイルが無い場合は前例ビューアでその旨を表示し、結果から外し、そのディレクトリの再スキャンを予約する。
- `size` や `mtimeNs` が違う場合は、読み直した内容で判定し直し、再インデクスを予約する。
- ファイルは変わっていないのに局面が見つからない場合は、Rust のパーサーと tsshogi の解釈の違いである。
  前例ビューアで該当する局面が見つからないことを表示し、ログに記録する。

インデクスが古いことによる誤った結果は利用者には見えない。
起こり得るのは、新しく追加された棋譜がまだ結果に出ないことだけである。
これを補うため、前例タブには各ルートの最終更新日時と更新中の状態を表示する。

## UI

UI の操作は頻度の異なる次の 3 つに分かれ、それぞれ別の場所に置く。

| 操作                                              | 頻度 | 置き場所                                          |
| ------------------------------------------------- | ---- | ------------------------------------------------- |
| 対象フォルダの管理 (追加・削除・再スキャン・進捗) | まれ | 管理ダイアログ (メニューから開く)                 |
| 現在の局面での検索                                | 頻繁 | 「前例」タブ (主な導線)、メニュー、ショートカット |
| 結果の棋譜を開く                                  | 頻繁 | 前例タブの一覧 → 前例ビューア (別ウィンドウ)      |

### メニュー

「ファイル」メニューの「一括変換」の近くに、サブメニュー「棋譜データベース」を追加する。

- フォルダの管理…
- 前例を検索 (前例タブを表示して選択する)

一括変換と同じくフォルダを対象にする機能であるため「ファイル」メニューに置く。
トップレベルのメニューは増やさない。

### 管理ダイアログ

- ルートごとに 1 行で、パス・状態 (最新 / 更新中 xx% / 利用不可)・局数・最終更新日時と、
  再スキャン・場所の変更・削除のボタンを表示する。
- ダイアログ下部に「フォルダを追加」ボタンを置く。
- 読み込みに失敗したファイルの件数を表示し、ファイル名と理由の一覧を確認できるようにする。
- 作成はバックグラウンドで進み、ダイアログを閉じても止まらない。完了は `NotificationOverlay` で通知する。
- 設定ダイアログには入れない (状態と操作が中心であり、設定値の画面とは性格が違うため)。
  自動更新の有無などの設定値だけは設定ダイアログに置いてよい。

### 前例タブ

```
┌ 前例 ─────────────────────────────────────── [⟳] ┐
│ 1,234 局 (先手勝 52% / 後手勝 45%)                   │
│ 次の手: ▲7六歩 812局 53%  ▲2六歩 401局 50% …         │
│──────────────────────────────────────────────────────│
│ 2024/05/01  A vs B   先手勝  45手目  …/x.kif           │
│ 2024/04/28  C vs D   後手勝  45手目  …/y.csa           │
│ … (ページング)                                       │
└──────────────────────────────────────────────────────┘
```

- 盤面に表示中の局面に追従して検索する (定跡パネルと同じ使い方)。
- 標準レイアウトのタブ (`TabPane`) と、カスタムレイアウト (`CustomLayout`・`LayoutManager` の部品) の両方に追加する。
- `Tab.SEARCH` はエンジンの「思考」タブが使っているため、新しい値は `Tab.PRECEDENTS` (`"precedents"`) とする。
- 追従による検索はデバウンスしてから `search` を呼ぶ。前の検索は中断して破棄し、
  `searchId` が違う応答は捨てる (応答の順番が前後しても表示が崩れないようにするため)。
- 件数と集計は `search` が返った時点で表示する。一覧は仮想スクロールとし、見えている範囲のページだけを
  `getPage` で取得して描画する。全件を一度に描画しない。
- 一覧はインデクスのメタ情報と `nextMove` だけで表示し、棋譜ファイルは読まない。
  tsshogi での再確認は前例ビューアで開く時点で行う。
- ルートが 1 つも無い場合は、説明と「フォルダを追加」ボタンを表示し、管理ダイアログに案内する。

### 前例ビューア

前例タブの一覧で棋譜を選ぶと、別ウィンドウの前例ビューアで開く。
メインウィンドウの棋譜は置き換えない。

- ウィンドウ:
  - モニターウィンドウと同じく `createAuxiliaryWindow` で作る補助ウィンドウとし、
    エントリーポイント `record-viewer.html` (`src/renderer/record-viewer/`) を追加する。
  - ウィンドウは 1 つだけとし、別の棋譜を選ぶと内容を置き換えて前面に出す。
    開いている間に選んだ棋譜は background から IPC でビューアに送る。
  - メインウィンドウを閉じると一緒に閉じる。
- 表示内容: 盤面、棋譜 (分岐を含む)、コメント、棋譜情報。該当する手数を選択した状態で開く。
  - 閲覧専用とし、編集・エンジン・対局の機能は持たない。
  - 盤面の反転はビューア独自に持ち、メインウィンドウとは連動しない。
  - 盤面と棋譜の表示には既存の部品 (`BoardView`・`RecordView` など) を使う。
- 読み込み: ファイルの読み込みは既存の `api.openRecord(path)` を使い、文字コードの扱いはアプリ設定に従う。
  開いた時点で tsshogi で読み直して局面を確かめる (「検索結果が古い場合の扱い」)。
- 「メインウィンドウで開く」ボタン: 表示中の棋譜を、ビューアで選択中の手数でメインウィンドウに開く。
  - メインウィンドウの `store.openRecord(path, { ply })` を使う。
  - メインウィンドウの棋譜に未保存の変更がある場合 (`isRecordFileUnsaved`) は確認を挟む。
  - `AppState.NORMAL` 以外 (対局中・解析中など) ではボタンを無効にする。
- メインウィンドウの棋譜を置き換えないため、対局中や解析中でも前例を開いて見られる。

### 対象外

- Web 版・モバイル版: メニュー・タブ・レイアウト部品を `isNative()` で非表示にする。
- 局面を指定して検索する専用のダイアログ: 局面編集モードで局面を作れば前例タブが追従するため作らない。

## 未決事項

アルファ版の実装に入る前に決める。

- エントリーで棋譜の中の位置をどう表すか:
  - 分岐: 手数だけでは分岐の中の局面を特定できない。分岐を含めるなら、棋譜の木の中のノード番号
    (深さ優先の通し番号など) が必要になる。アルファ版は本譜だけとし、分岐のオプションを外す案がある。
  - 1 ファイルに複数局: メインウィンドウと前例ビューアは 1 ファイルを 1 局として読むため、
    2 局目以降をインデクスに入れても開けない。「1 ファイル = 1 局」とし、`gameIds` を 1 つにする案がある。
  - `nextMove` の表し方: 移動元 (81 マス + 打つ駒 7 種)・移動先・成りで 15 bit に収まる。
    最終局面 (次の手なし) や投了などの特殊な手を表す値を決める。
  - ルートをまたぐ検索結果: gameId はルートごとの番号であるため、rootId を含めて 1 件 8 byte に収まる詰め方を決める。
- メタ情報: 結果は終局の手と手番から判定する。千日手・持将棋・中断・不明を勝率の集計でどう扱うかを決める。
  日付は書き方がばらばら (`2024/05/01 10:00:00`、`2024年5月1日(水)`、CSA の `$START_TIME` など) であり、
  解釈できる書き方と、日付が無い場合にファイルの mtime で代用するかを決める。
- スキャンの前提: FAT・exFAT (USB メモリ)・SMB (NAS) で、ディレクトリの mtime が更新されるか、
  ファイルの識別子が安定しているかを確かめる。FAT の mtime は 2 秒単位である。
  Windows のファイル ID は 64 bit のため、`fs.stat(path, { bigint: true })` で取得する。
- 保存場所: Windows の `userData` は `%APPDATA%` (ローミングプロファイル) であり、1〜2 GB のインデクスを置くと
  ドメイン環境で同期の対象になる。ローカルの場所 (`%LOCALAPPDATA%` に相当) に置くか、保存先を選べるようにするかを決める。
  管理ダイアログにはルートごとのディスク使用量を表示する。
- 形式のバージョン: セグメントとマニフェストの先頭にバージョンを入れ、合わなければ作り直す。
- アプリを 2 つ起動した場合: ロックを取れたインデクスホストだけが書き込み、もう一方は読み取り専用とし、
  マニフェストの世代が変わったことを検知して読み直す。

## 実装の手順

最初の版をアルファ版としてリリースする。一時的な比較実験の段階は設けない。

1. 共有クレートの切り出し、インデクス形式と局面ハッシュの定義の確定、utilityProcess とワーカーの基盤。
2. KIF のパーサーとインデクスの作成。tsshogi との golden 比較のテスト。
3. 検索ワーカーと検索 API (`search`・`getPage`・`cancel`)、世代の参照カウント、開く時点での確認。
4. 管理ダイアログ・メニュー・前例タブ (一覧のみ)・前例ビューア。
5. 差分更新・書き込みの通知・セグメントの統合・ファイル監視。
6. KI2・CSA のパーサー。
7. 次の手ごとの集計、カスタムレイアウトへの対応。

ここまでをアルファ版とする。JKF にはアルファ版の後で対応する。

性能は、定跡の `src/tests/background/book/onthefly.bench.ts` と同じく、常設のベンチマーク (`vitest bench`) で測る。
インデクス形式に `nextMove` と棋譜のメタ情報を含めることは、手順 1 で確定させる。
