# Web アプリの更新配信とキャッシュ

Web 版 (`vite.config-pwa.mts` でビルドし GitHub Pages で配信するもの) の
Service Worker によるキャッシュと、更新版をユーザーへ届けるまでの振る舞いを定める。

Service Worker が登録されていれば適用されるため、ホーム画面へインストールした
PWA として起動した場合に限らず、ブラウザーのタブで開いている場合も対象となる。
Electron 版には Service Worker を登録しないため、この仕様は適用されない。

## 前提

GitHub Pages は HTTP ヘッダーを変更できず、配信されるファイルには
`Cache-Control: max-age=600` が付与される。
したがって新しいファイルが CDN に反映されるまで最大 10 分の遅延が生じる。
`sw.js` 自体はブラウザーが HTTP キャッシュを迂回して取得するため、
この 10 分が更新を検知できるようになるまでの下限となる。

## キャッシュ

`injectManifest` モードを使い、Service Worker の本体は [`src/sw.js`](../src/sw.js) に置く。
ビルド時に事前キャッシュの一覧だけが差し込まれる。

自動生成 (`generateSW`) ではなく手書きにしているのは、ナビゲーションのレスポンスへ
cross-origin isolation のヘッダーを足すためである (「cross-origin isolation」を参照)。
キャッシュの挙動は自動生成のときと同じものを `sw.js` で組み立てている。

### 事前キャッシュ

以下を対象とする。初回アクセス時に一括で取得され、オフラインでも利用できる。

- JS / CSS / HTML / Web App Manifest
- `favicon*.png`
- `icon/**/*.svg` (UI アイコン)
- `arrow/**/*.svg` (矢印)
- `board/**/*.svg` (局面図などで使用する盤の枠線)
- `stand/**/*.png` (駒台)
- `sound/**/*.mp3` (効果音)

**エンジンの成果物 (`engines/**`) は対象外とする。** 将来もっと大きなエンジンが
載る可能性があり、エンジンを使わない利用者にも転送コストがかかるため。加えて
事前キャッシュが重いほど初回アクセスの再読み込みが遅れる (「初回アクセスの
再読み込み」を参照)。`globIgnores` で除外しているのは、`**/*.js` が Emscripten の
グルーコードを拾ってしまうため。

### 実行時キャッシュ

盤・駒の画像 (`board/`, `piece/`) は種類が多く合計 4MB 近くあり、
ユーザーが実際に使用するのはその一部に限られるため、事前キャッシュには含めない。
実際に読み込まれたものだけをキャッシュする。

- キャッシュ名: `shogihome-board-images`
- 方式: `StaleWhileRevalidate`
- 最大エントリー数: 200
- 有効期限: 30 日

これらの URL にはファイル名にハッシュを含まないため、リリースで画像を差し替えても
キャッシュしたものと区別できない。キャッシュを返した上で裏側で再取得を行い、
次回以降の表示に反映する。

初回アクセス時に既定のテーマの画像がキャッシュされるため、
以降はオフラインでも盤面を表示できる。
オフラインのままテーマを切り替えた場合は画像を取得できない。

#### エンジンの成果物

マニフェスト・グルーコード・wasm (`engines/**` の `.json` / `.js` / `.wasm`)。

- キャッシュ名: `shogihome-engine-modules`
- 方式: `StaleWhileRevalidate`
- 最大エントリー数: 60
- 有効期限: 90 日

事前キャッシュしないため、**エンジンの利用はオンラインを前提とする。**
一度使ったエンジンは以降オフラインでも動くが、それは保証しない。
読み込みに失敗した場合はエンジンを一覧から除外した上で、その旨を画面に出す
(`describeEngineLoadError()`)。オフラインが原因の場合は接続が必要であることを伝える。

評価パラメータや定跡 (`.data` / `.bin` / `.nnue`) は下記の別のキャッシュに入る。

### ナビゲーションのフォールバック

Service Worker の制御下では、ナビゲーションリクエストを `index.html` にフォールバックさせる。
ただし Electron 専用のページ (`prompt.html`, `monitor.html`, `layout-manager.html`) は
除外し、それぞれのページを返す。

このルートは事前キャッシュのルートより**先に**登録する。Workbox はルートを登録順に
照合するため、順序を逆にすると事前キャッシュ側がナビゲーションを拾ってしまい、
下記のヘッダーが付かなくなる。

## cross-origin isolation

マルチスレッドの WebAssembly は `SharedArrayBuffer` を要求し、これはページが
cross-origin isolated でなければ使えない。isolation には
`Cross-Origin-Opener-Policy: same-origin` と
`Cross-Origin-Embedder-Policy: require-corp` のレスポンスヘッダーが要るが、
GitHub Pages はヘッダーを設定できない。

そこで Service Worker が返すナビゲーションのレスポンスにこの 2 つを足す。
ヘッダーが必要なのはドキュメントだけであり、`require-corp` が `CORP` を要求するのは
**クロスオリジンの**サブリソースに対してである。Web 版は外部のサブリソースを
一切読み込まないため、他の応答に手を加える必要はない。

### 初回アクセスの再読み込み

ドキュメントを受け取った時点ではまだ Service Worker の制御下に無いため、
初回アクセスのドキュメントにはヘッダーが付かない。`crossOriginIsolated` は
ドキュメント生成時に確定し以後変わらないので、**isolated にするには
ドキュメントを作り直す (再読み込みする) しかない。**

そのため [`src/coi-bootstrap.js`](../src/coi-bootstrap.js) を `index.html` の
`<head>` へインラインで埋め込み、初回アクセスに限り Service Worker を登録してから
再読み込みする。埋め込みは `vite.config-pwa.mts` が行うため Electron 版には含まれない。

**描画してから再読み込みしてはならない。** 画面がちらつく上に描画の処理も無駄になる。
ブートストラップは `window.__shogihomeCOIReady` に Promise を置き、
`src/renderer/index.ts` がこれを待ってからアプリを起動する。
再読み込みする場合はこの Promise を解決しない。

無限ループを避けるため、再読み込みしたことを `sessionStorage` に記録する。
次のいずれかに当てはまる場合は再読み込みせず、isolated でないまま起動する
(その場合エンジンは使えるが、`SharedArrayBuffer` を要求するものは動かない)。

| 状況                                       | 動作                       |
| ------------------------------------------ | -------------------------- |
| 既に isolated (2 回目以降)                 | 即座に起動する             |
| Service Worker が使えない                  | 再読み込みしない           |
| `sessionStorage` が使えない                | 再読み込みしない           |
| 再読み込み済みなのに isolated にならない   | 再度は読み込み直さない     |
| Service Worker が 10 秒以内に有効にならない | 諦めて起動する             |

**代償は初回アクセスの表示が遅くなること。** Service Worker が有効になるには
事前キャッシュの完了が必要 (Workbox の `PrecacheController.install()` は
`event.waitUntil()` を呼ぶ) で、その間は描画しないため。回線を絞った実測値は次の通り。
2 回目以降のアクセスには影響しない。

| 回線       | 再読み込みなし | 再読み込みあり |
| ---------- | -------------- | -------------- |
| 400 KB/s   | 4.1 秒         | 9.4 秒         |
| 1500 KB/s  | 1.4 秒         | 3.4 秒         |
| 5000 KB/s  | 0.8 秒         | 1.9 秒         |

### その他

- `Cross-Origin-Opener-Policy: same-origin` により、`openWebBrowser()` が開いた
  タブから `window.opener` が辿れなくなる。外部リンクを開くだけなので影響はない。

エンジン側の制約は [`wasm-engine-abi.md`](./wasm-engine-abi.md) の「制約」を参照。

## 更新の検知

更新版を自動では適用しない (`registerType: "prompt"`)。
対局中や検討中に予期せずページが再読み込みされるのを防ぐため。

ブラウザーによる Service Worker の更新確認はページ遷移時と 24 時間ごとに限られ、
インストールした PWA を開いたまま使い続けるユーザーには更新が届かない。
そのため `src/renderer/webapp/update.ts` で以下のタイミングでも明示的に確認を行う。

- 1 時間ごと
- 画面が再び表示された時 (`visibilitychange`)

ただし直前の確認から 5 分以内は確認を省略する。
ページの読み込み直後もブラウザーが確認済みであるため省略する。

## 更新の適用

1. 更新版の Service Worker のインストールが完了したら、画面下部に通知を表示する。
   - この時点で更新版のファイルは取得済みであり、以降はオフラインでも適用できる。
   - 初回アクセス時のインストール (制御中の Service Worker が存在しない場合) では通知しない。
   - 同じ Service Worker について繰り返し通知はしない。
2. 通知を押すと更新を適用する。
   - 編集中の棋譜は localStorage へ自動保存され、再読み込み後に復元されるため、
     保存に関する確認は行わない。
3. 適用時は待機中の Service Worker へ `SKIP_WAITING` を送信し、
   制御が切り替わった時点 (`controllerchange`) でページを再読み込みする。
   - 5 秒以内に切り替わらない場合はそのまま再読み込みする。

通知を閉じた場合や操作しなかった場合は更新されない。
その場合も、全てのタブとウィンドウを閉じて開き直せば更新版が使用される。

## 開発時の扱い

開発サーバー (`npm run serve`) では既定で Service Worker を無効にする。
古いキャッシュが返ることによる混乱を避けるため。
PWA としての挙動を確認する場合は `PWA_DEV=1` を指定する。
