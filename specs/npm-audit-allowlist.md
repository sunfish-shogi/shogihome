# npm audit の除外リスト

定期実行の監査ワークフロー (`.github/workflows/audit.yml`) は、`docs/release.json` に記載された最新版 (`latest`) と安定版 (`stable`) のタグをそれぞれチェックアウトし、`npm audit` を実行する。
レビューの結果、このプロジェクトでは問題にならないと判断したアドバイザリは、除外リストに登録して監査の対象から外す。

## 構成

- `.github/audit-allowlist.json` — 除外リスト
- `scripts/audit-check.mjs` — `npm audit --json` の出力を除外リストと照合して合否を判定するスクリプト

npm audit には特定のアドバイザリを無視する機能がないため、判定は自前のスクリプトで行う。
スクリプトは Node.js の組み込みモジュールだけを使い、外部のツールに依存しない。

監査対象はリリース済みのタグで、そのチェックアウトには現在の除外リストもスクリプトも含まれない。
そのため、ワークフローはタグをチェックアウトする前に、実行したブランチ (通常は `main`) から両方を `$RUNNER_TEMP` に退避して使う。
除外リストの変更は `main` にマージした時点で、すべての監査対象バージョンに適用される。

## 除外リストの形式

```json
[
  {
    "id": "GHSA-xxxx-xxxx-xxxx",
    "package": "some-package",
    "reason": "ビルド時にのみ使用され配布物に含まれない。信頼できない入力を渡す経路もない。",
    "expires": "2027-03-31"
  }
]
```

| キー      | 必須 | 内容                                                       |
| --------- | ---- | ---------------------------------------------------------- |
| `id`      | ○    | GitHub Advisory ID (GHSA ID)。CVE ID は使わない            |
| `package` | ○    | 脆弱性のあるパッケージ名 (npm audit が報告する `name`)     |
| `reason`  | ○    | 問題ないと判断した理由                                     |
| `expires` | ○    | 除外の有効期限 (`YYYY-MM-DD`、UTC)。この日の終わりまで有効 |

- 照合は `id` と `package` の組で行う。同じ GHSA ID が別のパッケージで報告された場合は除外されない。
- 未知のキー、必須キーの欠落、不正な形式、重複したエントリがあると、監査そのものを失敗とする。
- GHSA ID を持たないアドバイザリは除外できない。

## 判定

1. `npm audit --json` のレポートから、各脆弱性の `via` に含まれるアドバイザリを集める (文字列の `via` は依存先パッケージへの参照なので数えない)。
2. 深刻度が閾値 (`--level`、ワークフローでは `critical`) 以上のアドバイザリを判定対象とする。
3. 判定対象のうち、有効期限内の除外エントリに一致するものを除く。
4. 1 件でも残れば失敗 (終了コード 1) とする。

次の場合も失敗とする。

- レポートに `error` が含まれる (ネットワークエラーなどで npm audit が完了しなかった)
- レポートが JSON として読めない、または未知の形式 (`auditReportVersion` が 2 以外) である
- レポートの構造が想定と異なる (脆弱性のエントリがオブジェクトでない、`via` が配列でないか空である、`via` が参照するパッケージがレポートにない、など)

次の場合は警告を出すが、失敗にはしない。GitHub Actions 上では警告をアノテーションとして表示する。

- 有効期限切れのエントリがある (一致するアドバイザリがあれば、そのアドバイザリによって失敗する)
- どのアドバイザリにも一致しないエントリがある

除外リストは最新版と安定版の監査で共有するため、片方のバージョンにしか一致しないエントリでは、もう片方の監査で「一致しない」警告が出る。
どの監査対象バージョンにも一致しなくなったエントリは削除する。

## 運用

- 除外を追加する前に、脆弱なコードが配布物に含まれるか、攻撃者が制御できる入力が届くかを確認し、その根拠を `reason` に書く。
- `expires` は長くても半年程度とする。期限が来たら改めて評価し、延長するか、依存の更新で解消する。
- 依存の更新で解消できる場合は、除外よりも更新を優先する。ただし、リリース済みのタグは更新できないため、次のリリースまでの間は除外で対応してよい。

ローカルで判定を試す場合は次のように実行する。

```bash
npm audit --json > audit-report.json
node scripts/audit-check.mjs --allowlist .github/audit-allowlist.json --level critical audit-report.json
```
