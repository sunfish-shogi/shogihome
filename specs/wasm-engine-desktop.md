# デスクトップ版の WebAssembly エンジン

デスクトップ版 (Electron) で、WebAssembly エンジンをダウンロードして使うための仕組み。

- エンジン管理画面の「ダウンロード」から、一覧に載ったエンジンを取得して登録できる
- 既存の「追加」は、ローカルのファイルを選ぶ操作であることが分かるよう「ファイルから追加」とした

エンジン側が満たすべき仕様は [`wasm-engine-abi.md`](./wasm-engine-abi.md)、Web 版の作りは
[`wasm-engine.md`](./wasm-engine.md) にある。デスクトップ版は同じエンジンの成果物をそのまま使う。

## 前提

- **Fuses の `runAsNode` は無効のまま** (`.electron-builder.config.mjs`)。`ELECTRON_RUN_AS_NODE` で
  Electron の実行ファイルを Node として使うことはできない
- **OS に依存する実行ファイルは同梱しない**

## 全体構成

```
scripts/engine-index.ts             一覧を更新・検証するスクリプト (add / verify)
src/tests/engines/index.spec.ts     一覧の検証

src/common/wasm-engine/package.ts   一覧とパッケージの型と検証

src/background/usi/wasm/
  engine-index.json                   ダウンロードできるエンジンの一覧 (アプリに同梱する)
  install.ts                          ダウンロード・検証・配置・削除
  process-electron.ts                 utility プロセスの起動 (ChildProcess と同じインターフェース)
  process-cmd.ts                      コマンドラインツール向けの代替 (起動できない)
  host.ts                             utility プロセスのエントリ (dist/packed/wasm-engine-host.js)
  runner.ts                           Node 上でエンジンを起動する (Electron に依存しない)
  protocol.ts                         background と utility プロセスの間のメッセージ

src/renderer/view/dialog/EngineDownloadDialog.vue   ダウンロード画面
```

## 実行

`USIEngine.path` が `engine.json` を指すエンジンは、`EngineProcess` (`src/background/usi/engine.ts`)
がプロセス型のエンジンの代わりに `WasmEngineProcess` で起動する。これ以降の USI の処理は
プロセス型のエンジンと共通で、統計情報・prompt ウィンドウ・早期 ponder・headless の
`addEngine` もそのまま使える。

`WasmEngineProcess` は `utilityProcess.fork()` で `host.ts` を起動する。utility プロセスは
Electron 自身の実行ファイルを `--type=utility` で起動したもので、`ELECTRON_RUN_AS_NODE` を
使わない。**そのため `runAsNode` を無効にしたまま動く。** `host.ts` は asar に同梱されるため
`onlyLoadAppFromAsar` とも両立する。

`utilityProcess.fork()` は app の `ready` イベントの後でなければ呼べない。そのため headless
モード (`--add-engine`) の処理も `app.whenReady()` の後に実行する。また utility プロセスが
V8 の続行できないエラーで終了するときに発生する `error` イベントは必ず購読し、エンジンの
エラーとして伝える (購読しないと background プロセスごと落ちる)。終了は続く `exit` で伝える。

`host.ts` は `runner.ts` を使い、Web 版の Worker (`engine.worker.ts`) と同じ手順を
ローカルのファイルで行う。

- グルーコードは `esm` なら `import()`、`umd` なら CommonJS のスコープで評価する。`umd` に渡す
  `require` はグルーコードのパスを基準に `createRequire` で作る。webpack は `createRequire` の
  呼び出しを置き換えてしまうため、host のバンドル (`webpack.config.mjs` の `wasm-engine-host`) では
  `module.parser.javascript.createRequire` を無効にしている
- `locateFile` はグルーコードの隣のパスを返す。`.wasm` と `.data` はそこに置かれている
- `dataFiles` はファイルから読み、Emscripten の仮想ファイルシステムへ書き込む
- `assetBaseURL` は参照しない。ダウンロード時に全てのファイルを手元へ集めてあるため
- `requiresCrossOriginIsolation` は参照しない。Node では cross-origin isolation の制約が無く、
  `SharedArrayBuffer` を使える。**スレッドを使うエンジンもそのまま動く**

WebAssembly エンジンは `quit` でプロセスを終了しない (`wasm-engine-abi.md`)。プロセス型の
エンジンと同じく `quit` で終わるよう、`host.ts` が `quit` を中継した後にエンジンの `terminate()`
を呼んでプロセスを終了する。`kill()` はまず `terminate` を依頼し、1 秒で応答が無ければ
utility プロセスを強制終了する。

エンジンのグルーコードが `console` に書いたものは USI のログに残す。

エンジンのメタデータ (`loadUSIEngineMeta`) では、`engine.json` を指すエンジンをシェルスクリプトと
みなさない。中身がテキストなので内容による判定ではシェルスクリプトになってしまうが、実際には
utility プロセスで直接動くため、スレッド数やハッシュサイズの見積もりから除外しない。

## 一覧 (インデックス)

ダウンロードできるエンジンの一覧は、リポジトリの **`src/background/usi/wasm/engine-index.json`**
で管理し、**アプリに同梱する。オンラインでは取得しない。**
配信元はリポジトリの外 (Cloudflare など) で、一覧は絶対 URL でそれを指す。

一覧はパッケージを構成する全てのファイルの sha256 を持ち、ダウンロードしたものは全てこれと
照合する (グルーコードは utility プロセスで Node の権限を持って動くため)。一覧をオンラインで
配信すると、配信元やそれを管理するアカウントが乗っ取られた場合に、一覧ごと
書き換えて、リリースを経ずに既存の全インストールへ任意のエンジンを配れてしまう。同梱した
一覧と照合すれば、配信元のファイルが書き換えられてもダウンロードが失敗するだけで済む。

一覧の変更は、次のアプリのリリースから使える。

```json
{
  "format": "shogihome-engine-index/1",
  "engines": [
    {
      "id": "yaneuraou",
      "version": "2026-09-01",
      "name": "YaneuraOu",
      "author": "yaneurao",
      "description": "任意の説明",
      "licenses": ["GPL-3.0-or-later"],
      "packageURL": "https://engines.example.com/yaneuraou/2026-09-01/",
      "files": [
        { "path": "engine.json", "sha256": "…", "size": 2684 },
        {
          "path": "yaneuraou.wasm",
          "url": "https://assets.example.com/yaneuraou.wasm",
          "sha256": "…",
          "size": 367783
        }
      ]
    }
  ]
}
```

| フィールド    | 必須 | 内容                                                                                   |
| ------------- | ---- | -------------------------------------------------------------------------------------- |
| `id`          | ○    | `[A-Za-z0-9][A-Za-z0-9._-]*` (末尾は `.` 以外)。インストール先のディレクトリ名にも使う |
| `version`     | ○    | 同じ文字種。内容が変わったら必ず変える                                                 |
| `name`        | ○    | 一覧に出す名前                                                                         |
| `author`      | ○    | 作者                                                                                   |
| `description` |      | 一覧に出す説明                                                                         |
| `licenses`    | ○    | 一覧に出す SPDX 識別子。全文は `engine.json` の `licenses` が指す                      |
| `packageURL`  | ○    | `engine.json` を置いたディレクトリの絶対 URL。末尾は `/`                               |
| `files`       | ○    | パッケージを構成する全てのファイル。`engine.json` を必ず含む                           |

`files` の要素は、インストール先での位置 (`path`)、取得先 (`url`。省略時は `packageURL` からの
`path`)、`sha256` と `size` を持つ。

URL は https のみ受け付ける (開発用に localhost の http だけは認める)。
`id` は大文字と小文字を区別せずに重複してはならない。インストール先のディレクトリ名になり、
Windows や macOS の既定のファイルシステムでは大文字と小文字の違いだけでは別の場所にならないため。
`files` の `path` は、大文字と小文字を区別せずに重複してはならず、あるファイルのパスが別の
ファイルのディレクトリになってもならない (例: `foo` と `foo/bar`)。どちらもインストールできないため。
パッケージの直下の `install.json` (大文字と小文字を区別しない。`install.json/…` も含む) は
インストーラーが書き込むメタデータの名前なので、`path` には使えない。
`path` の各部分は、Windows の予約名 (`CON`・`PRN`・`AUX`・`NUL`・`COM0`〜`COM9`・`LPT0`〜`LPT9`。
`NUL.js` のように拡張子が付いていても同じ。大文字と小文字は区別しない) であってはならず、
`.` で終わってもならない (`id` と `version` も同じ)。Windows ではインストールできないか、
末尾の `.` が取り除かれて別のファイルと衝突するため。

**不正な項目は実行時に除外し、他の項目は使えるようにする。** 1 件の誤りで全員がどのエンジンも
ダウンロードできなくなるのを避けるためで、除外した理由はログに残す。誤りそのものは
公開前に検出する (「一覧の検証」を参照)。全体の形式 (`format` や `engines` の型) が
違う場合だけは一覧ごと拒否する。

一覧は手で書かず、`scripts/engine-index.ts` で更新する。書き込む前に、一覧全体が実行時と同じ
検証を通ることを確かめる。

### エンジンの登録

エンジンは `add` で登録する。同じ `id` があれば置き換える (更新)。

**一覧に載せるのは本家が管理するエンジンに限る。**
第三者が管理するエンジンを載せる予定は無いため、配布者を示す項目や
「ShogiHome の一部ではない」といった表示は持たない。

```bash
npm run engine-index -- add https://engines.example.com/yaneuraou/2026-09-01/ \
  --id yaneuraou [--description "…"] [--version 2026-09-01]
```

`add` はパッケージの全てのファイルを実際に取得し、大きさと sha256 を求めて一覧に書き込む。
`version` を省略すると、全ファイルのパスと sha256 から作る (内容が変われば変わる)。
`engine.json` は一度だけ取得し、ライセンスやファイルの構成を読んだその中身の sha256 を記録する。
取り直すと、その間に配信中のものが差し替わった場合に、別の版の中身が混ざるため。
取得先はマニフェストの規則 (`wasm-engine-abi.md` の「6. (d)」) に従う。

| ファイル                                | 取得先                                 | インストール先           |
| --------------------------------------- | -------------------------------------- | ------------------------ |
| `engine.json`・グルーコード・ライセンス | `packageURL`                           | `engine.json` からの相対 |
| `<module>.worker.js` (あれば)           | `packageURL`                           | グルーコードの隣         |
| `.wasm`・`.data` (あれば)               | `assetBaseURL` (無ければ `packageURL`) | グルーコードの隣         |
| `dataFiles[].url`                       | `assetBaseURL` (無ければ `packageURL`) | `engine.json` からの相対 |

書き込んだ一覧は commit し、次のアプリのリリースに含める。

### 一覧の検証

`src/tests/engines/index.spec.ts` (Vitest) が次を確かめる。`npm test` と CI
(`.github/workflows/test.yml`) で実行される。

- 一覧の全ての項目が実行時の検証を通ること
- 全ての URL が https であること (実行時の検証が開発用に認める localhost の http を載せない)

**一覧が指すファイルは取得しない。** 大きなファイルのダウンロードを伴い、配信側の障害で
無関係な変更のテストまで落ちるため。登録のときに `add` が取得して確かめる。

### 配信中のファイルの検証

一覧が指すファイルが実際に配信され、壊れていないことは `verify` で確かめる。
一覧に載った全てのファイルを配信先から取得する。

```bash
npm run engine-index:verify                       # 一覧の全てのエンジン
npm run engine-index:verify -- --id yaneuraou     # 1 つのエンジンだけ
```

- ファイルが取得できること (404 などになっていないこと)
- 大きさと sha256 が一覧と一致すること。ストリームで照合し、宣言より大きくなった時点で打ち切る
- `engine.json` が参照するファイル (グルーコード・`dataFiles`・ライセンス全文) が一覧に載っていること
- `engine.json` がライセンスを申告していて、その SPDX 識別子が一覧の `licenses` と一致すること
  (インストール時と同じ判定。`validateManifestLicenses`)
- 一覧の全ての項目が実行時の検証を通ること

一覧は書き換えない。問題が 1 つでもあれば終了コード 1 で終わる。配信側の障害の影響を
受けるため CI には組み込まず、エンジンを登録した後や、配信先を変えた後などに手で実行する。

#### 配信側の要件

Web 版の要件 (`wasm-engine-abi.md` の「配信側の要件」) に加えて次を満たすこと。
デスクトップ版は Chromium のネットワークスタック (`net.fetch`) で取得し、
`User-Agent` に `ShogiHome/<版>` を名乗る。

- **ボット対策のチャレンジを返さない。** Cloudflare の Bot Fight Mode・Browser Integrity
  Check・JS チャレンジはアプリからの取得を 403 や HTML で拒否する。該当するパスでは無効にする
- **Referer を要求しない。** ホットリンク保護の対象外にする
- **置いたファイルを書き換えない。** 内容を変えるときは別の `version` のディレクトリに置く。
  一覧は sha256 で照合するため、書き換えると検証に失敗して誰もインストールできなくなる。
  古い版のディレクトリも消さない。配布済みのアプリは、自分が同梱する一覧の版を取得し続ける

CORS と CORP はブラウザが強制するものなので、デスクトップ版の取得には影響しない。

## 検証

**ダウンロードしたものは全て一覧の sha256 と大きさで照合する。** グルーコードは utility
プロセスで Node の権限を持って動く。wasm もビルド設定によってはグルーコードの関数を通じて
任意の処理を行える。評価パラメータや定跡もエンジンの解析処理の入力になる。壊れた
評価パラメータはエラーにならずに「弱い」「おかしい」という形で現れるため、事故の検出にも役立つ。

照合はダウンロードしながら行い、大きさが宣言を超えた時点で打ち切る (ダウンロード前に表示するライセンス全文も同じ)。1 つでも一致しなければ
インストールしない。取得したマニフェストが仕様を満たすこと、グルーコード・`dataFiles`・
ライセンス全文が一覧に載っていることも確かめる。

ダウンロード前のライセンスの取得 (`engine.json` とライセンス全文) には時間の上限 (60 秒) を設ける。
この間は画面が操作できず取り消せないため、配信側が応答の途中でデータを送らなくなっても
待ち続けないようにする。上限に達したら読み取りを打ち切ってエラーにする。

起動時には照合しない。利用者のフォルダを書き換えられる攻撃者は、登録済みのプロセス型の
エンジンも差し替えられるため、新たな脅威にはならない。一覧を読むときにファイルの有無と
大きさだけを確かめ、欠けていれば「修復が必要」と示す。

一覧そのものは HTTPS で取得したものを信頼している。一覧に署名を付けて検証する仕組みは
まだ無い (「今後」を参照)。

## 配置

```
<userData>/engines/                  ポータブル版では実行ファイルの隣の engines/
  <id>@<version>/
    engine.json                        USIEngine.path はこれを指す
    install.json                       インストールの記録 (一覧の項目と sha256)
    <module>.js / <module>.wasm / …
  .tmp-<id>@<version>-<乱数>/          ダウンロード中
  .trash-<id>@<version>-<乱数>/        置き換えで退避した古いもの
```

- ダウンロードは `.tmp-*` に行い、全て揃って検証が通ったらリネームして確定する
- 同じ版が既にある場合 (再インストール・修復) は、古いものを `.trash-*` へ退避してから置き換える。
  新しいものを置けなかった場合は、退避した古いものを元に戻す
- **キャンセルは、ファイルを置く直前と、置いた後のエンジンの起動の直後で確かめる。** 置く前に
  キャンセルされた場合は何もインストールしない。起動の後にキャンセルされた場合は一覧に登録しない
  (ファイルは検証済みなので残し、「インストール済み」に未使用として表示する)。利用者が
  キャンセルした場合はエラーを表示しない
- **手元に同じ sha256 のファイルがあれば、ダウンロードせずに複製する。** 更新で評価パラメータが
  変わらない場合や、壊れたファイルだけを修復する場合に、大きなファイルを取り直さないため。
  複製したものも照合し、一致しなければダウンロードに切り替える
- Windows ではセキュリティソフトが書き込み直後のファイルを掴み、リネームが `EPERM` などで
  失敗することがある。少し待って繰り返す
- 起動時に、1 日以上前の `.tmp-*` と `.trash-*` を消す。macOS では複数のインスタンスを
  起動できるため、別のインスタンスがダウンロード中のものは消さない
- アンインストールはディレクトリごと消す。エンジンが動いている間と、保存済みの一覧から参照されて
  いる間は消さない。保存済みの一覧は消す時点で読み直す。macOS では複数のインスタンスが同じ一覧と
  インストール先を共有するため、ダウンロード画面を開いた後に別のインスタンスが保存した参照も
  確かめる必要がある。参照しているかどうかはパスの文字列ではなくファイルとして同じかどうかで判定し、
  シンボリックリンク経由のパスや大文字と小文字だけが違うパスで登録されたものも見落とさない

## 登録

インストールしたエンジンは一度起動して (`getUSIEngineInfo`)、実機が申告する作者と
オプションを得る。これをそのまま **1 件だけ**エンジン一覧に登録する。「ファイルから追加」と
同じ扱いで、オプションの値は上書きしない。

**表示名 (`name` と `defaultName`) はマニフェストの `name` にする。** USI の `id name` には
評価関数やビルドの違いが反映されないことが多く、同じエンジンの別の配布物と見分けが
付かないため (例: Sunfish4-Lite は `id name Sunfish4` を返す)。

**マニフェストのプリセット (`presets`) は使わない。** プリセットは Web 版でエンジンを一覧に
並べるためのもので、レベル別の設定などもそこで提供している。デスクトップ版では、利用者が
オプション画面や「複製」で自由に設定を作れる。ただし**タグだけは生かす。** 全てのプリセットの `tags` を集めて重複を除いたもの (OR) を
エンジンのタグにする。例えば一部のプリセットだけが `game` を持つ場合でも、登録した
エンジンには「対局」のタグが付く。

**加えて、定義済みのタグ「ダウンロード」を付ける** (`getPredefinedUSIEngineTag("download")`)。
ダウンロードしたエンジンを一覧で見分けたり、絞り込んだりできるようにするため。
タグは他の定義済みのタグ (対局・検討・詰み探索) と同じく、登録した時点の言語の文字列で
保存される。**保存済みの設定に残るため、訳語は後から変えられない。**

| 言語       | タグ         |
| ---------- | ------------ |
| 日本語     | ダウンロード |
| 英語       | Downloaded   |
| 繁体字     | 已下載       |
| ベトナム語 | Đã tải xuống |

オプション画面は、プロセス型のエンジンと同じく実機から定義を取り直す。

## 画面

エンジン管理画面の下部に「ファイルから追加」「ダウンロード」「比較・マージ」を並べる。
エンジンが 1 つも無いときは「エンジンをダウンロード」も表示する。どちらも Web 版では出さない。

ダウンロード画面はエンジン管理画面の子の画面である。**エンジン管理画面は一覧をメモリ上で
編集し「保存して閉じる」で確定する**ため、ダウンロード画面も結果をエンジン管理画面の一覧に
返すだけにし、確定は任せる。ファイルの保存だけはその場で確定する。

| 操作                          | 振る舞い                                                                                                                                                                                                                     |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| インストール                  | ライセンス全文を表示し、同意したらダウンロードする。エンジンを 1 件、一覧に足す                                                                                                                                              |
| 更新 (別の版がある)           | 編集中の一覧で古い版を参照している項目を新しい版に向ける。オプションの定義・既定の名前・作者は新しい版から取得したものにし、**URI**・表示名・利用者が変えたオプションの値 (型が同じもの)・タグは引き継ぐ。参照が無ければ足す |
| 再インストール (同じ版がある) | 欠けたファイルや壊れたファイルを修復する。編集中の一覧に参照があれば一覧は変えず、無ければ足す                                                                                                                               |
| アンインストール              | 編集中の一覧と保存済みの一覧のどちらからも参照されていない場合だけ行える                                                                                                                                                     |

**一覧をどう変えるかは編集中の一覧だけで決める** (`src/renderer/helpers/enginePackage.ts`)。
「保存して閉じる」で保存されるのは編集中の一覧なので、保存済みの一覧にだけ残っている項目は
保存すれば消える。例えば項目を削除して保存せずに再ダウンロードした場合は、項目を足す。
保存済みの一覧はアンインストールの可否の判定にだけ使う (キャンセルされると参照が残るため)。
判定の順序は次のとおり。

1. インストールした版を参照する項目が編集中の一覧にあれば、一覧は変えない。古い版を参照する
   項目が並んでいても書き換えない (利用者が意図して両方を登録している場合に、修復で古い版の
   項目が消えないようにするため)
2. 同じ id の他の版を参照する項目があれば、それらを新しい版に向ける (更新)
3. どちらも無ければ足す

URI を変えないのは、対局や検討の設定が URI でエンジンを参照しているためである。
更新後の古い版は「インストール済み」に「未使用」として残り、利用者が消す。

ライセンスの確認では、ライセンス全文とソースコードの入手先 (`source`) を示す。
**`engine.json` がライセンスを申告していないパッケージや、その SPDX 識別子が一覧の `licenses` と
一致しないパッケージは、表示もインストールもしない。** 全文を示してから同意を得ることが前提のため。
全文は `engine.json` と一緒にダウンロード前に取得し、一覧の sha256 で照合する。
コピーレフトのライセンスに限った注意書きは出さない。条件がかかるのは再頒布する側で、
使うだけの利用者には義務が無いため (注意書きがあると、使うだけでも義務が生じるように読める)。

ダウンロードされ、ShogiHome 本体とは別のプロセスで動き、USI の文字列だけをやり取りする。
