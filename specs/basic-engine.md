# basic エンジンの実装状況

ShogiHome が自前で持つ WebAssembly エンジン (`engines/basic/`) の中身と、
今後の改良に必要な情報をまとめる。

- 動かす仕組み (ShogiHome 側): [`wasm-engine.md`](./wasm-engine.md)
- エンジンが満たすべき仕様: [`wasm-engine-abi.md`](./wasm-engine-abi.md)

**この文書は実装を変えたら更新すること。** 特に「採用している手法」と
「未実装の手法」の表は、改良の起点になるので実態とずれないようにする。

---

## 1. 位置づけ

Web 版で対局相手を用意するための最小限のエンジン。強さよりも次を優先している。

- 単一スレッドで動く (`-pthread` を使えない。理由は ABI 仕様書の「制約」を参照)
- 探索を中断できる (`poll()` 1 回につき 1 反復)
- 依存を持たない (評価パラメータのファイルも定跡も無い)

現在の実力の目安は、自己対局で深さ 5 が深さ 3 に対して 7 割前後で勝つ程度。
人間の初級者を相手にする水準で、上級者の相手は想定していない。

## 3. 局面の表現

- **9x9 の mailbox**。`Square` は `(rank - 1) * 9 + (file - 1)` の単純な添字。
  ビットボードは使っていない。
- 指し手生成は方向テーブル (`MOVE_TYPE_TABLE`) を辿る素朴な実装。
  飛車・角・香は空きマスが続く限り伸ばす。
- **疑似合法手を生成し、`doMove()` の失敗で弾く。** 自玉の王手放置・二歩・
  打ち歩詰め・行き所のない駒はここで判定する。生成の段階では絞り込まない。
- 局面のキーは 2 通り持つ。
  - `Position::hashKey()` — **Zobrist ハッシュ** (64bit)。置換表のキーに使う。
    `doMove` / `undoMove` の中で XOR による差分更新を行うので取得は定数時間。
    乱数表は固定シード (`core/zobrist.cpp`) で、実行のたびに変わらない。
    盤上の駒・持ち駒 (色と枚数)・手番を含む。将棋では盤面が同じでも持ち駒が違えば
    別局面になるので、持ち駒を含めることが必須。
  - `Position::key()` — SFEN 文字列。千日手の判定とテスト・デバッグ用。
    探索の内側では使わない (ヒープ確保が起きるため)。

tsshogi (`src/renderer/players/basic.ts` が使うライブラリ) と指し手生成が
一致することは、移植時に 6388 局面で確認済み。

## 4. 評価関数

**駒割 + 持ち駒ボーナス + 落とし穴法 (piece square table) の和**。末端局面でのみ計算し、
差分計算は行わない (指し手の並べ替えにだけ駒割の差分を使う)。

### 駒割 (`evaluate.cpp`)

| 駒  | 値  | 駒   | 値   |
| --- | --- | ---- | ---- |
| 歩  | 100 | と金 | 400  |
| 香  | 300 | 成香 | 500  |
| 桂  | 400 | 成桂 | 500  |
| 銀  | 500 | 成銀 | 600  |
| 金  | 600 | 馬   | 1200 |
| 角  | 700 | 龍   | 1500 |
| 飛  | 800 | 玉   | 0    |

### 持ち駒ボーナス (`HAND_BONUS` = 15)

持ち駒は上の駒割に **1 枚あたり 15 点** を上乗せする。持ち駒はどのマスにも打てるぶん
盤上の駒より働きが広く、また打ってしまうと選択肢が減るため。

**これが無いと、打っても打たなくても駒割が変わらない。** 盤上に出れば落とし穴法の
ぶんだけ評価値が上がるので、目先の位置評価のために取ったばかりの駒を無駄打ちしてしまう。
落とし穴法より小さく、かつ駒の損得を覆さない大きさ (最小の駒である歩の 15%) に取ってある。

新旧のビルドで 20 局を戦わせたときの「打つ手」の割合。

| ビルド     | 打つ手 / 全手数    |
| ---------- | ------------------ |
| ボーナス無 | 228 / 1380 (16.5%) |
| ボーナス有 | 183 / 1381 (13.3%) |

勝敗は 7 勝 5 敗 8 分で、この局数では強さの差は読み取れない
(勝率の判断には 100 局以上が要る)。狙いどおり打つ手が減ったことのみ確認できている。

指し手の並べ替えに使う `materialDelta()` でも、駒を取る手で持ち駒が増えるぶんに
同じボーナスを乗せている。ただし駒を取る手には一律で乗るため、並び順は変わらない。

### 落とし穴法 (`pst.cpp`)

駒の種類ごとに 9x9 の表を持ち、先手視点で定義して後手は 180 度回転で参照する。
玉・飛・角・金・銀は居飛車と振り飛車で左右の使い分けが逆になるため、
戦型ごとに別のテーブルを持つ。

**値は駒割に対して十分に低くする。**

### 評価していないもの

玉の安全度、駒の利き、歩の形 (連結・垂れ歩・浮き駒)、駒の連携など、
位置以外の要素は一切見ていない。

## 5. 探索

### 採用している手法

| 手法                   | 実装箇所                      | 備考                                                                          |
| ---------------------- | ----------------------------- | ----------------------------------------------------------------------------- |
| Negamax                | `negamax()`                   | 手番側から見た評価に統一                                                      |
| α-β 枝刈り             | `negamax()` / `quiescence()`  | fail-hard (`score >= beta` で `beta` を返す)                                  |
| 反復深化               | `BasicEngine::runIteration()` | **中断可能にするのが主目的。前反復の結果を並べ替えに使っていない**            |
| 静止探索               | `quiescence()`                | 駒を取る手のみ。王手されていれば全合法手。最大 8 手                           |
| Stand pat              | `quiescence()`                | 王手されていない場合のみ下限として使う                                        |
| 指し手順序付け         | `orderMoves()`                | 置換表の手 → 駒を取る手 → killer move → その他                                |
| killer move            | `Context::recordKiller()`     | 深さごとに 2 手。駒を取らない手で β 遮断を起こした手を覚える                  |
| Zobrist ハッシュ       | `core/zobrist.*`              | 64bit。`doMove` / `undoMove` で差分更新                                       |
| 置換表                 | `tt.*`                        | 深さが足りていれば枝刈り。大きさは `USI_Hash` (既定 16MB)                     |
| 置換表の手を先頭に置く | `orderMoves()` の hint        | 根では前の反復の最善手になる。枝刈りより効くことも多い                        |
| null move pruning      | `negamax()`                   | 減らす深さは 2。王手中と詰みの窓では使わない。深さ 4 以上で効く               |
| 三角配列による PV 保持 | `Context::pv` / `pvLength`    | `info ... pv` の出力用。最大 24 手                                            |
| 詰みスコアの手数補正   | `-MATE_SCORE + ply`           | 短い詰みほど高評価。`score mate N` の出力にも使う                             |
| ルートでの千日手回避   | `search()`                    | 指した後の局面が棋譜中に 1 回以上出現していれば `-1000`。連続王手は区別しない |
| ルートでの乱数         | `search()`                    | 0〜3 を加算。詰みスコアには加えない。`Randomize` で無効化できる               |
| 打ち切り判定           | `Context::checkLimits()`      | ノード数上限と締切。時刻の確認は 2048 ノードごと                              |

ルートの窓 `alpha = bestScore - JITTER_RANGE` は aspiration window ではなく、
**乱数を加えても選ばれ得ない手を早く枝刈りするためのもの**。
再探索が要らない範囲に切ってあるので fail-low しても何もしない。

### 千日手の扱い (連続王手の千日手は未対応)

実装されているのは**根での単純な回避だけ**。`search()` が、指した後の局面が
`historyKeys` (`position ... moves ...` から復元した棋譜) に 1 回でも出ていれば
探索せずに `-REPETITION_PENALTY` (=`-1000`) を与える。同形 4 回という本来の成立条件より
かなり手前で避けるので、対局中に千日手へ突入すること自体は稀。

**連続王手の千日手は区別していない。** 千日手に至る手順が連続王手だったかどうかを
一切見ておらず、どちらの側が王手を続けていても同じ `-1000` になる。
本来のルールでは王手を続けた側の反則負けであり、ShogiHome 本体
(`src/renderer/game/game.ts` の `record.perpetualCheck`) は実際にそう裁定するため、
エンジンの認識とアプリの裁定がずれる。具体的には次の 2 つで損をする。

- **自分が王手を続ける側のとき**: `-1000` は負けの評価値ではない。
  形勢が `-1000` より悪いと判断している局面では連続王手の千日手が
  「最も損の小さい手」に見えてしまい、自ら反則負けの手順に入り得る。
  正しくは `-MATE_SCORE` 相当を与えるべきところ。
- **相手が王手を続ける側のとき**: 本来はこちらの勝ちだが、
  同じ `-1000` の罰点で避けてしまい、勝ちを逃す。

加えて、**探索木の中には千日手の判定が一切無い** (根でしか見ていない)。
そのため読み筋の中で千日手が絡む変化はどちらの種類も評価できない。

実装するなら次の形になる。`Position::inCheck(Color)` は既にあるので判定材料は揃っている。

1. `historyKeys` と並べて「その局面が王手された局面か」を持ち回る
   (`UsiDriver::onPosition()` で `doMove` のたびに記録する)
2. 同形を見つけたとき、間に挟まる片側の手が全て王手だったかを調べる
3. 連続王手なら `±1000` ではなく `±MATE_SCORE` 相当を返す

「探索木の中での千日手判定」と同時に入れるのが自然なので、
未実装の手法の表でも一つの項目としてまとめている。

### 置換表の扱い

記録するのは残り深さ・評価値・その評価値の意味 (`Bound`)・最善手。
入れ替えは「別の局面なら古い世代か浅い結果のときだけ置き換える」方式で、
同じ局面なら深い結果を優先する。

注意している点。

- **詰みの評価値は根からの手数で表しているため、そのまま記録できない。**
  記録時に「この局面から何手か」へ直し、取り出すときに戻す
  (`scoreToTT` / `scoreFromTT`)。
- **根の結果は深さ -1 で記録する。** 根の評価値は正確とは限らない
  (窓を絞って探索した手は上界としか分からず、乱数で選んだ手は最善とも限らない)。
  `negamax` が引くのは深さ 1 以上のときだけなので、-1 なら枝刈りには使われず、
  次の反復の指し手順序付けにだけ効く。
- **枝刈りした枝では三角配列に読み筋が残らない。** そのままだと表示される
  読み筋が短くなるため、根で足りないぶんを置換表から辿って補っている。
- 対局の開始 (`usinewgame`) で全て捨てる。`go` のたびに世代を進め、
  前の手のエントリは指し手順序付けに使いつつ置き換えの対象にする。

キーの衝突は 64bit なので実用上は無視できるが、取り出した指し手は
`doMove()` が失敗すれば捨てられるので、非合法手を指すことはない。

### 未実装の手法 (改良候補)

上から順に費用対効果が高いと考えている。

| 手法                       | 期待できること                                               |
| -------------------------- | ------------------------------------------------------------ |
| **history heuristic**      | killer で拾えない手の順序付け。手の (移動元, 移動先) ごとに  |
|                            | 遮断の実績を貯める。killer と同じ枠組みに載せられる          |
| **SEE (静的交換評価)**     | 駒損する取り合いを静止探索で読まずに済む                     |
| 静止探索でも置換表を引く   | 現在は `negamax` でしか引いていない                          |
| LMR (Late Move Reductions) | 指し手順序付けが効いてから入れる                             |
| Aspiration window          | 反復間で窓を絞る。評価が安定してから                         |
| 王手延長・一手詰め判定     | 終盤の精度                                                   |
| 千日手の判定 (探索木の中 / | 現在は根で `-1000` を与えるだけ。連続王手の側を反則負けと    |
| 連続王手)                  | 見なしていないため、自ら反則負けに入ることも勝ちを逃すことも |
|                            | ある。Zobrist キーがあるので実装可能                         |
| Bitboard                   | 指し手生成の高速化。書き換え量が大きい                       |

**残るボトルネックは駒を取らない手の順序付け。** 置換表の手が無い局面では
駒割の差分しか手掛かりが無く、静かな局面ほど枝刈りが効きにくい。

### null move pruning の扱い

「1 手パスしても β 以上」なら、実際に指せばもっと良くなるはずなので枝を捨てる。
`Position::doNullMove()` は手番と Zobrist キーの手番ぶんを反転させるだけ。

将棋は手番を渡すこと自体が損になる局面 (Zugzwang) が稀なので、チェスの終盤ほど
危険ではない。それでも次の場合は使わない。

- **王手されている**: パスすると玉を取られる手順を読んでしまう
- **β が詰みの評価値**: 詰みの有無をパスで判定してはいけない
- **深さが足りない**: 減らす深さ (2) を引いた残りが無いと意味が無い

深さ 4 以上でしか発動しない (根が深さ 3 のとき `negamax` に渡る深さは 2 まで)。
つまり **Lv. 2 のプリセット (深さ 3) には影響せず、Lv. 3 (深さ 5) だけが速くなる。**

連続した null move を禁じる処理は入れていない。`Depth` の上限が 5 なので、
1 回パスすると残り深さが 2 になり、発動条件 (3 以上) を満たさなくなるため。
`Depth` の上限を上げる場合はこの前提が崩れるので注意する。

導入時の計測 (深さ 5、`npm run engines:bench`)。

| 局面     | ノード数        | 時間           |
| -------- | --------------- | -------------- |
| 初期局面 | 61208 → 50200   | 45ms → 37ms    |
| 序盤     | 59088 → 35837   | 65ms → 44ms    |
| 中盤     | 503595 → 440826 | 448ms → 357ms  |
| 終盤     | 深さ 3 → 深さ 4 | 打ち切り (3秒) |

**探索を完了できた局面では、最善手も評価値も導入前と一致した。**
純粋な高速化として働いており、読みの質は落ちていない。
同じ持ち時間での自己対局は 12 局で 2 勝 0 敗 10 分 (引き分けが多く決着が付きにくいため、
この局数では強さの差は測れない。少なくとも悪化はしていない)。

### killer move の扱い

同じ深さで β 遮断を起こした**駒を取らない手**を 2 手まで覚えておき、
次に同じ深さを調べるときに駒を取る手の次に試す。兄弟ノードでも同じ手が
有効なことが多い、という経験則による。

駒を取る手を対象にしないのは、元々駒割で先に並ぶため。
記録は探索 (反復) ごとに作り直す (`Context` が持つ)。

指し手の優先度は次の順。点数の間隔は駒の価値 (取ると最大 3000) より十分大きく取り、
種別の順序が駒割で逆転しないようにしている。

| 優先度 | 内容               | 点数          |
| ------ | ------------------ | ------------- |
| 1      | 置換表の手         | 1000000       |
| 2      | 駒を取る手・成る手 | 100000 + 駒割 |
| 3      | killer move        | 10000 / 9999  |
| 4      | それ以外           | 0             |

点数は比較のたびではなく先に計算する。比較関数の中で求めると O(n log n) 回
呼ばれることになり、終盤の局面で無視できない差になる (532ms → 382ms)。

導入時の計測 (`npm run engines:bench`)。

| 局面     | 深さ | ノード数        | 時間           |
| -------- | ---- | --------------- | -------------- |
| 初期局面 | 3    | 2089 → 1548     | 12ms → 12ms    |
| 中盤     | 3    | 8038 → 4797     | 11ms → 10ms    |
| 終盤     | 3    | 571794 → 324064 | 719ms → 382ms  |
| 初期局面 | 5    | 50200 → 31346   | 37ms → 29ms    |
| 序盤     | 5    | 35837 → 28846   | 44ms → 36ms    |
| 中盤     | 5    | 440826 → 229548 | 357ms → 177ms  |
| 終盤     | 5    | 717223 → 454922 | 打ち切り (3秒) |

**null move pruning と違い、深さ 3 でも効く** (26〜43% の削減)。
Lv. 2 のプリセットも速くなる。

探索を完了できた局面では最善手も評価値も導入前と一致した。
対局と同じ持ち時間 (1 手 150ms) では、中盤の局面で到達深さが 3 から 4 に上がる。

同じ持ち時間での自己対局は 36 局で 12 勝 13 敗 11 分。**この局数では強さの差は
測れない** (勝率の差を主張するには 100 局以上が要る)。採用の根拠は
「固定深さでの結果が変わらないこと」と「同じ時間でより深く読めること」であって、
自己対局の結果ではない。

### 置換表を入れたときの効果 (記録)

同じ局面・同じ深さでのノード数と時間 (`npm run engines:bench`)。

| 局面     | 深さ | ノード数        | 時間           |
| -------- | ---- | --------------- | -------------- |
| 初期局面 | 3    | 4502 → 2089     | 13ms → 14ms    |
| 中盤     | 3    | 23607 → 8038    | 25ms → 11ms    |
| 終盤     | 3    | 649792 → 571794 | 856ms → 696ms  |
| 初期局面 | 5    | 313777 → 61208  | 201ms → 45ms   |

**中盤で深さ 5 に届くようになった**のが一番大きい。終盤の局面 (持ち駒が多く

定跡、ponder (先読み)、マルチスレッド。ponder の扱いは

## 6. 時間制御

`BasicEngine::computeBudgetMs()` が 1 手あたりの上限を決める。

| 条件                   | 割り当て      |
| ---------------------- | ------------- |
| `go infinite` / ponder | 10000ms       |
| 秒読みあり             | 秒読み × 4/5  |
| 加算あり               | 加算 × 4/5    |
| 切れ負け               | 残り時間 ÷ 40 |

最後に 100ms〜3000ms へ丸め、さらに **実際に使える時間で頭打ちにする**。
使える時間は `残り時間 + 秒読み + 加算` で、秒読みと加算は持ち時間を使い切った後も
使えるので足して考える (ShogiHome は加算ぶんを引いた `btime` を送ってくるため足し戻す)。
これが無いと 100ms の下限が持ち時間を超え、切れ負けの終盤で時間切れになる。
`MinimumThinkingTime` (擬似思考時間) も同じくこの割り当てを超えないように頭打ちにする。

深さ 1 は `go` の中で必ず終わらせ、深さ 2 以降は `poll()` 1 回につき 1 反復進める。
打ち切られた反復の結果は捨て、1 つ前の深さの結果を採用する。

**深さ 1 だけは締切を無視する。** 持ち時間を使い切っていても指し手を 1 つは
確保するため。ここで打ち切られると `pendingBestMove_` が空のまま `bestmove` を出すことになり、
`flushBestMove()` が `resign` を返してしまう。とくに秒読みでは `btime 0` が普通なので、
上の頭打ちと組み合わせると割り当てが 0 になり得る。深さ 1 は静止探索を含めても
持ち駒の多い終盤で 10ms 程度なので、超過は無視できる。

残り時間ごとの `bestmove` までの実測値。

| 条件                  | 頭打ち前 | 頭打ち後 |
| --------------------- | -------- | -------- |
| 切れ負け 残り 0ms     | 103ms    | 10ms     |
| 切れ負け 残り 50ms    | 103ms    | 52ms     |
| 切れ負け 残り 1 秒    | 107ms    | 103ms    |
| 秒読み 5 秒 (btime 0) | 509ms    | 509ms    |
| 加算 3 秒 (btime 0)   | 508ms    | 506ms    |

秒読みと加算が変わらないことが重要。**残り時間だけで頭打ちにしてはならない。**
`btime 0` で割り当てが 0 になり、秒読み対局のほぼ全局面で投了する。

**1 手 3 秒の上限はスマートフォンでは長い。** 探索が速くなったら見直す余地がある。

## 7. オプション

| 名前                  | 型    | 既定        | 内容                                                      |
| --------------------- | ----- | ----------- | --------------------------------------------------------- |
| `Style`               | combo | static_rook | `static_rook` / `ranging_rook` / `random`                 |
| `Depth`               | spin  | 3           | 探索の深さ (1〜5)                                         |
| `MinimumThinkingTime` | spin  | 500         | 最低思考時間 (ミリ秒)                                     |
| `USI_Hash`            | spin  | 16          | 置換表の大きさ (MB)。1〜256                               |
| `Randomize`           | check | true        | 根の乱数。無効にすると探索が決定的になる (ベンチマーク用) |
| `USI_Ponder`          | check | false       | 先読み。未実装                                            |

プリセット (一覧に並ぶエンジン) の構成は [`wasm-engine.md`](./wasm-engine.md) を参照。

## 8. 動作確認の方法

改良を入れたら、下から順に確認する。**速くなったことと強くなったことは別**なので、
ベンチマークだけで判断しないこと。

### 8-1. C++ のテスト

```bash
npm run engines:test
```

ネイティブビルドして CTest を実行する。局面・指し手生成・USI の解析・評価・探索の
基本的な性質を確認する (`engines/tests/basic_test.cpp`)。Emscripten は要らない。

### 8-2. WebAssembly のテスト

```bash
npm run engines:build   # エンジンを変更したら必ず再生成する
npm test
```

`src/tests/engines/` が commit 済みの wasm に対して走る。

- `conformance.spec.ts` — ABI の適合性。`public/engines/` 配下を自動で検証する
- `basic-wasm.spec.ts` — 探索と評価の性質、時間制御、オプションの効き方

**ネイティブビルドでしか確認できないこと・wasm でしか確認できないことがある。**
例えば Emscripten は既定で例外を捕捉しないため、`std::stoll` の例外で abort する
不具合はネイティブでは再現しない。両方を通すこと。

### 8-3. ベンチマーク (速さ)

```bash
npm run engines:bench
```

性質の異なる 5 局面を深さ 3 と 5 で探索し、ノード数・時間・NPS を表で出す。

`Randomize` を無効にして探索を決定的にしているので、**ノード数は毎回同じ値になる。**
改良の前後で比較するには次のようにする。

```bash
npm run engines:bench -- --json > /tmp/before.json
# ここで改良する
npm run engines:bench -- --json > /tmp/after.json
diff <(jq -r '.results[] | "\(.position) \(.requestedDepth) \(.nodes)"' /tmp/before.json) \
     <(jq -r '.results[] | "\(.position) \(.requestedDepth) \(.nodes)"' /tmp/after.json)
```

時間は環境に左右されるので、**ノード数を主な指標にする。**
`打切` の列に `*` が付いた行は 1 手あたりの上限で打ち切られており、
ノード数と時間の対応が取れないので比較に使えない。

### 8-4. 自己対局 (強さ)

```bash
npm run engines:selfplay -- --a Depth=5 --b Depth=3 --games 20
```

設定を変えた二者を戦わせて勝率を出す。先後は 1 局ごとに入れ替える。
千日手と手数上限は引き分けとして扱う。

**乱数が入るため結果はばらつく。** 少数の対局で強さを判断しないこと。
目安として、勝率の差が 10% 程度あることを主張するには 100 局以上が要る。
時間を短くすると回せる局数が増える。

```bash
npm run engines:selfplay -- --a Depth=5 --b Depth=3 --games 100 \
  --go "go btime 60000 wtime 60000 byoyomi 500"
```

### 8-5. 駒組の確認

戦型ごとの囲いが崩れていないかは自己対局の棋譜を見る。

```bash
npm run engines:selfplay -- --a Style=static_rook --b Style=ranging_rook --games 2 --verbose
```

`--verbose` で棋譜 (USI) が出るので、40 手前後で矢倉と美濃囲いに組めているかを確認する。
落とし穴法のテーブルを触ったら必ず見ること。

### 8-6. ブラウザでの確認

```bash
npm run serve
```

- `http://localhost:5173/` — 対局ダイアログにエンジンが並ぶこと、対局できること
- `http://localhost:5173/?mobile` — モバイルのレベル選択から対局できること
- DevTools の Application → Workers に Worker が生成されていること
- 対局中に「中断」して即座に着手が返ること (`stop` が効くこと)

自動化する場合は Playwright から `src/renderer/ipc/api.ts` を直接叩くのが手軽で、
`api.usiLaunch()` → `api.usiReady()` → `api.usiGo()` の流れをそのまま再現できる。

### 8-7. 対話実行

```bash
npm run engines:native
./engines/build-native/basic
```

標準入出力で USI コマンドを直接やり取りできる。詳細は
[`engines/README.md`](../engines/README.md) を参照。
