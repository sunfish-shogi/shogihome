# basic エンジンの実装状況

ShogiHome が自前で持つ WebAssembly エンジン (`engines/basic/`) の中身と、
今後の改良に必要な情報をまとめる。

- 動かす仕組み (ShogiHome 側): [`wasm-engine.md`](./wasm-engine.md)
- エンジンが満たすべき仕様: [`wasm-engine-abi.md`](./wasm-engine-abi.md)

**この文書は実装を変えたら更新すること。** 特に「採用している手法」と
「未実装の手法」の表は、改良の起点になるので実態とずれないようにする。

---

## 1. 位置づけ

Web 版で対局相手を用意するための最小限のエンジン。強さよりも次を優先している。

- 単一スレッドで動く (`-pthread` を使えない。理由は ABI 仕様書の「制約」を参照)
- 探索を中断できる (`poll()` 1 回につき 1 反復)
- 依存を持たない (評価パラメータのファイルも定跡も無い)

現在の実力の目安は、自己対局で深さ 5 が深さ 3 に対して 7 割前後で勝つ程度。
人間の初級者を相手にする水準で、上級者の相手は想定していない。

## 3. 局面の表現

- **9x9 の mailbox**。`Square` は `(rank - 1) * 9 + (file - 1)` の単純な添字。
  ビットボードは使っていない。
- 指し手生成は方向テーブル (`MOVE_TYPE_TABLE`) を辿る素朴な実装。
  飛車・角・香は空きマスが続く限り伸ばす。
- **疑似合法手を生成し、`doMove()` の失敗で弾く。** 自玉の王手放置・二歩・
  打ち歩詰め・行き所のない駒はここで判定する。生成の段階では絞り込まない。
- 局面のキーは SFEN 文字列 (`Position::key()`)。Zobrist ハッシュは持たない。
  千日手の判定にしか使っておらず、置換表を入れる際は Zobrist が要る。

tsshogi (`src/renderer/players/basic.ts` が使うライブラリ) と指し手生成が
一致することは、移植時に 6388 局面で確認済み。

## 4. 評価関数

**駒割 + 落とし穴法 (piece square table) の和**。末端局面でのみ計算し、
差分計算は行わない (指し手の並べ替えにだけ駒割の差分を使う)。

### 駒割 (`evaluate.cpp`)

| 駒  | 値  | 駒   | 値   |
| --- | --- | ---- | ---- |
| 歩  | 100 | と金 | 400  |
| 香  | 300 | 成香 | 500  |
| 桂  | 400 | 成桂 | 500  |
| 銀  | 500 | 成銀 | 600  |
| 金  | 600 | 馬   | 1200 |
| 角  | 700 | 龍   | 1500 |
| 飛  | 800 | 玉   | 0    |

盤上と持ち駒で同じ価値を使う。

### 落とし穴法 (`pst.cpp`)

駒の種類ごとに 9x9 の表を持ち、先手視点で定義して後手は 180 度回転で参照する。
玉・飛・角・金・銀は居飛車と振り飛車で左右の使い分けが逆になるため、
戦型ごとに別のテーブルを持つ。

**値は駒割に対する味付けに留め、1 マスあたり最大 30 (歩の 3 割)。**
駒組の手が駒の損得を上回らないようにするため。既定値は居飛車が矢倉
(玉8八・金7八・金6七・銀7七・飛2八)、振り飛車が美濃囲い
(玉3八・金4九・金5八・銀3九) に組むように調整してある。

### 評価していないもの

玉の安全度、駒の利き、歩の形 (連結・垂れ歩・浮き駒)、駒の連携など、
位置以外の要素は一切見ていない。

## 5. 探索

### 採用している手法

| 手法                   | 実装箇所                      | 備考                                                               |
| ---------------------- | ----------------------------- | ------------------------------------------------------------------ |
| Negamax                | `negamax()`                   | 手番側から見た評価に統一                                           |
| α-β 枝刈り             | `negamax()` / `quiescence()`  | fail-hard (`score >= beta` で `beta` を返す)                       |
| 反復深化               | `BasicEngine::runIteration()` | **中断可能にするのが主目的。前反復の結果を並べ替えに使っていない** |
| 静止探索               | `quiescence()`                | 駒を取る手のみ。王手されていれば全合法手。最大 8 手                |
| Stand pat              | `quiescence()`                | 王手されていない場合のみ下限として使う                             |
| 静的な指し手順序付け   | `orderMoves()`                | `materialDelta()` の降順に安定ソート                               |
| 三角配列による PV 保持 | `Context::pv` / `pvLength`    | `info ... pv` の出力用。最大 24 手                                 |
| 詰みスコアの手数補正   | `-MATE_SCORE + ply`           | 短い詰みほど高評価。`score mate N` の出力にも使う                  |
| ルートでの千日手回避   | `search()`                    | 指した後の局面が棋譜中に 1 回以上出現していれば `-1000`            |
| ルートでの乱数         | `search()`                    | 0〜3 を加算。詰みスコアには加えない。`Randomize` で無効化できる    |
| 打ち切り判定           | `Context::checkLimits()`      | ノード数上限と締切。時刻の確認は 2048 ノードごと                   |

ルートの窓 `alpha = bestScore - JITTER_RANGE` は aspiration window ではなく、
**乱数を加えても選ばれ得ない手を早く枝刈りするためのもの**。
再探索が要らない範囲に切ってあるので fail-low しても何もしない。

### 未実装の手法 (改良候補)

上から順に費用対効果が高いと考えている。

| 手法                           | 期待できること                                               |
| ------------------------------ | ------------------------------------------------------------ |
| **置換表**                     | 同一局面の再探索を丸ごと省ける。Zobrist ハッシュの導入が前提 |
| **前反復の PV 手を先頭に置く** | 反復深化を持ちながら使っていない。α-β の効きが大きく変わる   |
| **killer move / history**      | 駒を取らない手の順序付け。現在は駒割の差分しか見ていない     |
| **SEE (静的交換評価)**         | 駒損する取り合いを静止探索で読まずに済む                     |
| Null move pruning              | 前向き枝刈り。詰み絡みでの扱いに注意が要る                   |
| LMR (Late Move Reductions)     | 同上。指し手順序付けが効いてから入れる                       |
| Aspiration window              | 反復間で窓を絞る。評価が安定してから                         |
| 王手延長・一手詰め判定         | 終盤の精度                                                   |
| Bitboard                       | 指し手生成の高速化。書き換え量が大きい                       |
| 詰み探索 (`go mate`)           | 現在は `checkmate notimplemented` を返す                     |

**現状の最大のボトルネックは置換表と指し手順序付けの不在。**
中盤で深さ 5 が 1 手 3 秒に収まらないのは主にこれが原因で、
この 2 つだけでも同じ時間で 1〜2 手深く読めるようになるのが普通。

### 探索していないもの

定跡、ponder (先読み)、マルチスレッド。ponder の扱いは
[`wasm-engine.md`](./wasm-engine.md) を参照。

## 6. 時間制御

`BasicEngine::computeBudgetMs()` が 1 手あたりの上限を決める。

| 条件                   | 割り当て      |
| ---------------------- | ------------- |
| `go infinite` / ponder | 10000ms       |
| 秒読みあり             | 秒読み × 4/5  |
| 加算あり               | 加算 × 4/5    |
| 切れ負け               | 残り時間 ÷ 40 |

最後に 100ms〜3000ms へ丸める。`MinimumThinkingTime` (擬似思考時間) は
この割り当てを超えないように頭打ちにする (超えると切れ負けで時間切れになる)。

深さ 1 は `go` の中で必ず終わらせ、深さ 2 以降は `poll()` 1 回につき 1 反復進める。
打ち切られた反復の結果は捨て、1 つ前の深さの結果を採用する。

**1 手 3 秒の上限はスマートフォンでは長い。** 探索が速くなったら見直す余地がある。

## 8. 動作確認の方法

改良を入れたら、下から順に確認する。**速くなったことと強くなったことは別**なので、
ベンチマークだけで判断しないこと。

### 8-1. C++ のテスト

```bash
npm run engines:test
```

ネイティブビルドして CTest を実行する。局面・指し手生成・USI の解析・評価・探索の
基本的な性質を確認する (`engines/tests/basic_test.cpp`)。Emscripten は要らない。

### 8-2. WebAssembly のテスト

```bash
npm run engines:build   # エンジンを変更したら必ず再生成する
npm test
```

`src/tests/engines/` が commit 済みの wasm に対して走る。

- `conformance.spec.ts` — ABI の適合性。`public/engines/` 配下を自動で検証する
- `basic-wasm.spec.ts` — 探索と評価の性質、時間制御、オプションの効き方

**ネイティブビルドでしか確認できないこと・wasm でしか確認できないことがある。**
例えば Emscripten は既定で例外を捕捉しないため、`std::stoll` の例外で abort する
不具合はネイティブでは再現しない。両方を通すこと。

### 8-3. ベンチマーク (速さ)

```bash
npm run engines:bench
```

性質の異なる 5 局面を深さ 3 と 5 で探索し、ノード数・時間・NPS を表で出す。

`Randomize` を無効にして探索を決定的にしているので、**ノード数は毎回同じ値になる。**
改良の前後で比較するには次のようにする。

```bash
npm run engines:bench -- --json > /tmp/before.json
# ここで改良する
npm run engines:bench -- --json > /tmp/after.json
diff <(jq -r '.results[] | "\(.position) \(.requestedDepth) \(.nodes)"' /tmp/before.json) \
     <(jq -r '.results[] | "\(.position) \(.requestedDepth) \(.nodes)"' /tmp/after.json)
```

時間は環境に左右されるので、**ノード数を主な指標にする。**
`打切` の列に `*` が付いた行は 1 手あたりの上限で打ち切られており、
ノード数と時間の対応が取れないので比較に使えない。

### 8-4. 自己対局 (強さ)

```bash
npm run engines:selfplay -- --a Depth=5 --b Depth=3 --games 20
```

設定を変えた二者を戦わせて勝率を出す。先後は 1 局ごとに入れ替える。
千日手と手数上限は引き分けとして扱う。

**乱数が入るため結果はばらつく。** 少数の対局で強さを判断しないこと。
目安として、勝率の差が 10% 程度あることを主張するには 100 局以上が要る。
時間を短くすると回せる局数が増える。

```bash
npm run engines:selfplay -- --a Depth=5 --b Depth=3 --games 100 \
  --go "go btime 60000 wtime 60000 byoyomi 500"
```

### 8-5. 駒組の確認

戦型ごとの囲いが崩れていないかは自己対局の棋譜を見る。

```bash
npm run engines:selfplay -- --a Style=static_rook --b Style=ranging_rook --games 2 --verbose
```

`--verbose` で棋譜 (USI) が出るので、40 手前後で矢倉と美濃囲いに組めているかを確認する。
落とし穴法のテーブルを触ったら必ず見ること。

### 8-6. ブラウザでの確認

```bash
npm run serve
```

- `http://localhost:5173/` — 対局ダイアログにエンジンが並ぶこと、対局できること
- `http://localhost:5173/?mobile` — モバイルのレベル選択から対局できること
- DevTools の Application → Workers に Worker が生成されていること
- 対局中に「中断」して即座に着手が返ること (`stop` が効くこと)

自動化する場合は Playwright から `src/renderer/ipc/api.ts` を直接叩くのが手軽で、
`api.usiLaunch()` → `api.usiReady()` → `api.usiGo()` の流れをそのまま再現できる。

### 8-7. 対話実行

```bash
npm run engines:native
./engines/build-native/basic
```

標準入出力で USI コマンドを直接やり取りできる。詳細は
[`engines/README.md`](../engines/README.md) を参照。
